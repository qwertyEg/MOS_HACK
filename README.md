# Мониторинг строительных площадок по кадрам видеонаблюдения

Кейс 07, ЛЦТ-2026. Департамент градостроительной политики Москвы.

Система принимает кадры с камер стройплощадки, определяет по ним текущие этапы
работ, сопоставляет с календарным планом и выдаёт вердикт — **отставание,
соответствие или опережение графика** — вместе с прогнозом задержки.

---

## Что внутри

Три механизма, на которых держится решение.

**Динамическая маска.** Оператор один раз закрашивает фон на первом кадре:
соседние дома, улицу, горизонт. Дальше маска **только сжимается** — растущее
здание отвоёвывает её обратно. Обратное физически невозможно: сама собой
застройка не исчезает.

Направление монотонности выбрано по тому, куда ведёт ошибка. Если бы росла
область объекта, сбой означал бы «скрыто всё, разбор сорван». При сжимающейся
маске фона сбой означает «показали лишний кусок фона», то есть откат к полному
кадру. Хуже, чем без маски, стать не может. Ошибки оператора тоже безобидны:
закрасил лишнего — стройка меняется, алгоритм сам её откроет; закрасил мало —
часть фона останется видимой, как и при работе без маски вовсе.

**Чек-лист вместо классификации.** Модель Б (VLM) не отвечает на вопрос «какой
здесь этап» — она отвечает на набор конкретных наблюдаемых вопросов: видна ли
опалубка, виден ли башенный кран, закрыт ли фасад. Ответ тернарный: да / нет /
**не уверена**. Третье значение позволяет кадру, где признак не разглядеть, не
голосовать вовсе, вместо того чтобы разбавлять статистику случайным «нет».
Версии чек-листов копятся по датам, и аналитика строится по всей хронологии.

**Темп в активных днях.** Заказчик потребовал два отдельных вывода — «работает
или стоит» и «предсказывай задержку». Они сведены в одну формулу: темп считается
не на календарный день, а на день, когда на площадке реально шла работа. Это
различает два случая, которые линейная экстраполяция путает: отставание из-за
двухнедельного простоя (темп нормальный, догонят) и отставание при полной
загрузке (темп низкий, разрыв будет расти).

## Быстрый старт

### 1. Модель Б

Модель намеренно **не входит в этот репозиторий** — подключается по
OpenAI-совместимому эндпоинту, чтобы можно было подставить свою.

```bash
docker run -d --name open-webui --gpus=all --restart unless-stopped \
  -e OLLAMA_HOST=0.0.0.0:11434 \
  -p 127.0.0.1:8081:8080 -p 127.0.0.1:11435:11434 \
  -v open-webui:/app/backend/data -v open-webui-ollama:/root/.ollama \
  ghcr.io/open-webui/open-webui:ollama

docker exec -it open-webui ollama pull qwen3-vl:30b
```

Порт **11435**, а не стандартный 11434: на машине разработки 11434 занят другим
процессом. При необходимости поменяйте `VLM_BASE_URL`.

Про выбор модели: `qwen3-vl:30b` — MoE, 30B суммарно при ~3B активных на токен.
Качество крупной модели при стоимости инференса мелкой, что хорошо ложится на
машину с большой унифицированной памятью. Если берёте 8B — указывайте тег
`qwen3-vl:8b-instruct` явно: голый `qwen3-vl:8b` тянет thinking-версию, которая
перед каждым ответом генерирует цепочку рассуждений, а нам нужны односложные
ответы и низкая латентность.

### 2. Сервис

```bash
cp .env.example .env          # при необходимости поправить
docker compose up -d --build
```

Поднимаются три сервиса: приложение (`:8000`), Postgres (`:5432`) и MinIO
(`:9000`, консоль `:9001`).

### 3. Справочники

```bash
python tools/parse_workbook.py    # Excel → reference/work_types.csv
docker compose exec app python -m app.seed
```

Откройте http://localhost:8000, вход `admin` / `admin`.


## Хранение данных

Кадры лежат в MinIO, а не в базе и не в контейнере приложения. Приложение можно
пересобрать или снести — снимки останутся. В Postgres хранится только ключ
объекта, размеры, время съёмки и хеш.

Если нужен другой S3 — меняется одна переменная `S3_ENDPOINT`, код не трогается.
Если S3 недоступен вовсе, есть локальный бэкенд: `STORAGE_BACKEND=local`.

## Инструменты

| Скрипт | Назначение |
|---|---|
| `tools/parse_workbook.py` | Сводный перечень работ → CSV, раскладка по макроэтапам |
| `tools/ingest_folder.py` | Прогон истории камеры через маску, без модели Б |
| `tools/mask_replay.py` | Покадровая раскладка работы маски в картинках |
| `tools/vlm_bench.py` | Замер модели Б: латентность, стабильность, точность |

### Прогон истории камеры

1. Завести объект и камеру в интерфейсе, указав путь к папке с кадрами.
   Имена файлов должны содержать метку времени: `doric_2006_11_23_12_30_21.jpg`.
2. Открыть карточку камеры и закрасить фон кистью, подтвердить.
3. Запустить прогон:

```bash
python tools/ingest_folder.py --list           # какие есть камеры
python tools/ingest_folder.py --camera 1
```

Результат — три картинки на каждый кадр: исходник, кадр с погашенным фоном
(ровно то, что ушло бы в модель Б) и наложение маски красным. Смотреть в
`/cameras/<id>/frames`, переключая представление.

### Разбор сводного перечня

Исходный Excel содержит баг: коды уровня 2 («10.1.», «12.3.») были
автоконвертированы в даты (45667 → 10.01.2025). Парсер их восстанавливает.

Из 377 строк справочника после раскладки остаётся **206** — остальное внутренние
работы, поставка оборудования и специфика линейных объектов, которые с камеры
не наблюдаются. Каждая строка несёт обоснование, по какому правилу она отнесена
к макроэтапу или исключена: `reference/work_types.csv`. Спорные случаи вынесены
отдельно в `reference/work_types_review.csv`.

### Замер модели Б

```bash
export VLM_BASE_URL=http://localhost:11435/v1
export VLM_MODEL=qwen3-vl:30b
python tools/vlm_bench.py data/Строительная_техника --limit 20 --repeat 2
```

Меряет три вещи, которые решают, годится модель: латентность в пересчёте на
кадр и на сутки работы камеры, стабильность ответа при повторе, и осмысленность
ответов по таблице.

## Тесты

```bash
.venv/bin/python -m pytest tests/ -q
```

Покрыты два места, ошибки в которых тихие и дорогие:

- **разбор ответа модели** — модель отвечает свободным текстом, а от результата
  зависит весь вердикт;
- **динамическая маска** на синтетической сцене, где есть все четыре объекта,
  ради которых метод строился: растущее здание, статичный сосед, шумное небо и
  разово мелькнувший грузовик. Проверяется, что здание захвачено, остальное нет,
  и что маска только растёт.

## Структура

```
app/
  main.py         FastAPI: API и серверный рендер страниц
  models.py       модель данных (она же схема — миграций нет)
  seed.py         справочники, макроэтапы, чек-листы
  storage.py      хранилище кадров: S3 или локальная ФС
  pipeline/
    mask.py       динамическая маска, детекция смены ракурса
    model_b.py    клиент VLM, заполнение чек-листа
  templates/      Jinja2 + HTMX, без сборки
tools/            автономные утилиты
reference/        разобранные справочники
tests/
```

Фронтенда со сборкой нет намеренно: разработка ведётся в одиночку, и отдельный
SPA означал бы второй сервис и npm в образе ради страниц, которые прекрасно
рендерятся на сервере.
