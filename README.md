# СтройВзор — мониторинг стройплощадки по снимкам камер

Кейс 07 ЛЦТ-2026 (Департамент градостроительной политики Москвы). Постановка задачи — `docs/TZ_case07.md`.

Камеры площадки присылают снимки раз в 20–30 минут, либо пользователь загружает папку, zip или видео.
По снимкам сервис отвечает на три вопроса:

1. **Какая техника на площадке и работает ли она.** Это модель А. Она находит и классифицирует технику,
   по двум соседним кадрам определяет «работает» или «стоит», считает одну машину один раз, даже если её
   видят несколько камер, и ведёт моточасы. Отработанное списывается из плановых часов этапа
   («временная полоска» по каждому типу техники).
2. **Какой идёт этап.** Это модель Б. Ночные, дождливые и бракованные кадры она пропускает. Чужие
   статичные здания гасит динамическая маска. По чек-листу признаков модель отвечает «да / нет / не уверен»
   и по монотонной хронологии (стройка не идёт назад) определяет текущий этап и его готовность.
3. **Всё ли идёт по плану.** Это аналитика. Она проверяет, та ли техника работает на этапе
   (экскаватор без самосвалов — снижение темпа), сверяет модели А и Б между собой (часы отработаны,
   а этап не сменился — задержка) и сравнивает план с фактом (отставание в днях, прогноз). Каждое
   отклонение объяснено словами и подкреплено снимками-доказательствами.

Любую модель можно переключить в интерфейсе: **локальные модели** (YOLO + SigLIP, без интернета, на CPU)
или **внешний API** (GLM-4.6V).

## Архитектура

```
core/            доменная логика без БД и HTTP (тестируется без GPU и сети)
  contracts.py   типы и протоколы — договор между модулями
  taxonomy.py    словарь: 21 тип техники, 8 этапов / 32 подэтапа, 60 признаков (reference/checklist.json)
  equipment/     модель А: YOLO / GLM-детектор, уточнение подтипа грузовиков (SigLIP), трекер,
                 статусы, склейка камер по гомографии, моточасы, отрисовка рамок
  stage/         модель Б: качество кадра, динамическая маска, чек-лист SigLIP / GLM / локальная VLM,
                 скоринг, монотонная хронология (HMM)
  plan/          каталог работ из xlsx организаторов, импорт календарного плана, нормы «этап → техника»
  analytics/     правила отклонений, план/факт и прогноз, отчёт по объекту
  vlm_client.py  клиент OpenAI-совместимых VLM (z.ai GLM-4.6V, Ollama/vLLM)
app/             веб-сервис FastAPI: БД (SQLite / PostgreSQL), хранилище кадров (диск / S3),
                 очередь кадров по камерам, конвейер, JSON API, страницы UI (Alpine.js + ECharts)
reference/       справочники: checklist.json, work_map.csv (перечень работ → этапы), equipment_rules.json
simcam/          имитатор камеры-потока
tools/           засев демо, загрузка папки/видео, сборка справочника, мок UI
models/          веса детектора (в git не кладём — см. models/README.md)
```

Конвейер кадра выглядит так: приём, затем оценка качества, затем модель А (каждый кадр, днём и ночью),
затем модель Б (только годные дневные кадры, не чаще раза в час на камеру, внеочередно — если сильно
изменилась маска). После этого с дебаунсом пересчитывается площадка: хронология этапов, моточасы,
отклонения, отчёт.

Договор модулей, схема БД, JSON API и экраны описаны в **`docs/ARCHITECTURE.md`**. Отдельная
карта стека и причин выбора технологий — в **`docs/TECH_STACK.md`**. Методика сопоставления
справочников и правила «этап → техника» — в **`docs/methodology.md`**.

Визуальное руководство по платформе — **`output/pdf/stroyvzor_platform_guide.pdf`**: преимущества,
полный конвейер, модели А и Б, экраны, настройка, установка, API, прогноз, измеренная точность,
ограничения и чек-лист ввода площадки в эксплуатацию.

## Быстрый старт

### Локально (Python 3.12)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt            # веб-сервис, конвейер, внешний API
pip install -r requirements-ml.txt         # локальные модели: torch (CPU), ultralytics, transformers
cp .env.example .env                       # при необходимости поправить
python -m app                              # http://localhost:8000, вход admin / admin (задаётся в .env)
```

По умолчанию данные хранятся в SQLite (`var/app.db`), кадры — в `var/storage`. Без `requirements-ml.txt`
сервис тоже работает: локальные провайдеры показывают «не готов» с причиной, а анализ идёт через внешний API.

### Docker

```bash
cp .env.example .env                       # задать POSTGRES_PASSWORD, ADMIN_PASSWORD, SECRET_KEY
docker compose up --build                  # приложение + PostgreSQL
docker compose --profile s3 up --build     # кадры в MinIO вместо ./var/storage
WITH_ML=0 docker compose up --build        # лёгкий образ: только внешний API
```

Веса монтируются из `./models` (там же лежит кэш HuggingFace для SigLIP), демо-данные — из `./datasets`
(только чтение).

### На сервере (общая машина, CPU)

Процесс один: очередь кадров и загруженные модели живут в памяти, поэтому uvicorn работает с одним
воркером. Для общей машины в репозитории есть постоянные systemd-юниты с лимитами CPU/RAM и пониженным приоритетом:

```bash
sudo cp deploy/mos-app.service deploy/mos-watchdog.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mos-watchdog mos-app
curl http://127.0.0.1:8000/api/health
```

Сервису хватает около 3 ГБ памяти: YOLO11s и одна общая копия SigLIP2. При старте модели текущего
режима загружаются заранее (`WARM_MODELS`), чтобы первый кадр не ждал загрузки около 50 секунд.
`mos-watchdog` останавливает только юниты/процессы из `/root/mos_hack`, если на общем сервере заканчиваются памя, GPU или диск; чужие задачи он не трогает.

Если машина целиком выделена приложению, можно снять ограничения базового юнита
и отдать локальным моделям все 8 CPU-потоков и GPU 0:

```bash
sudo install -d /etc/systemd/system/mos-app.service.d
sudo cp deploy/mos-app-dedicated.conf /etc/systemd/system/mos-app.service.d/dedicated.conf
sudo systemctl daemon-reload
sudo systemctl restart mos-app
```

PyTorch выбирает CUDA автоматически, когда драйвер действительно предоставляет
устройство вычисления; иначе YOLO и SigLIP продолжают работать на CPU.

Для временного командного демо по внешнему IP установите второй drop-in:

```bash
sudo cp deploy/mos-app-public.conf /etc/systemd/system/mos-app.service.d/public.conf
sudo systemctl daemon-reload
sudo systemctl restart mos-app
```

Он открывает стандартный HTTP-порт 80 на всех интерфейсах. Пароль администратора при этом
не должен быть значением по умолчанию; для постоянного доступа нужен TLS-прокси.

## Веса моделей

| Модель | Откуда | Куда |
|---|---|---|
| Детектор техники (модель А): YOLO11s, 12 классов, val mAP50 0.865 | обучен на GPU-сервере команды (`/root/mos_hack/models/`) | `models/equipment_yolo.pt` + `models/equipment_classes.json` |
| SigLIP2 (модель Б и уточнение подтипа грузовиков) | HuggingFace `google/siglip2-base-patch16-224`, скачивается сам при первом использовании | кэш HF (`HF_HOME`) |

Скрипта автоматической загрузки весов детектора нет (`tools/fetch_models.py` не реализован).
Веса копируются вручную с сервера команды:

```bash
scp <сервер>:/root/mos_hack/models/equipment_yolo.pt <сервер>:/root/mos_hack/models/equipment_classes.json models/
```

Если веса выложены в релиз GitHub, скачайте оба файла в `models/`. Для работы без интернета SigLIP нужно
скачать заранее (`huggingface-cli download google/siglip2-base-patch16-224`) и выставить
`HF_HUB_OFFLINE=1`. Формат `equipment_classes.json`, переменные `EQUIPMENT_*`, качество по классам и
скорость на CPU описаны в **`models/README.md`**.

Если своих весов нет, детектор переходит на YOLO-World без дообучения: сервис работает, но точность
ниже, и `ready()` честно об этом пишет. Классов `truck` и `crane_manipulator` нет в обучающих данных:
их даёт уточнение подтипа по кропу SigLIP (на тестовой выборке 8 из 9 и 8 из 12).

## Переключение провайдеров

В шапке UI есть переключатель режима, его дублирует страница «Настройки» (`PUT /api/settings`):

| Режим | Модель А | Модель Б | Нужно |
|---|---|---|---|
| **local** | `yolo` (YOLO + уточнение SigLIP) | `siglip` (чек-лист SigLIP2) | `requirements-ml.txt`, веса в `models/` |
| **external** | `glm` (GLM-4.6V с рамками) | `glm` (двухшаговый разбор GLM-4.6V) | `ZAI_API_KEY` в `.env` |
| **hybrid** | `yolo` | `glm` | и то и другое |

Модели можно выбрать и по отдельности. Модель Б умеет ещё `local_vlm` — любую VLM по
OpenAI-совместимому API (Ollama / vLLM, `VLM_BASE_URL`, `VLM_MODEL`). Готовность провайдеров с причиной
отказа показывают `/api/health` и `/api/settings`. Результаты хранятся с именем провайдера: при смене
провайдера старые не стираются, кнопка «Переанализировать» на объекте пересчитывает кадры заново.
Пороги (радиус склейки камер, «да/нет» чек-листа, окно пары техники и т. п.) правятся на странице
«Настройки».

## Демо-сценарий

Демо-данные — `datasets/demo/sites/<объект>/` (в git не кладутся). Каждый объект — это `site.json`
(название, план, парк техники, камеры, калибровка, зоны) и папки камер со снимками; метка времени
записана в имени файла. Засев:

```bash
python tools/seed_demo.py --root datasets/demo                 # засеять и обработать
python tools/seed_demo.py --root datasets/demo --no-process    # только засеять, анализ — в работающем сервисе
```

То же делает кнопка «Создать демо-объект» на странице «Обзор» (`POST /api/demo/seed`, каталог — `DEMO_DIR`).

Что показать:

1. **Обзор** — карточки объектов с вердиктом (отставание / соответствие / опережение), текущим этапом,
   техникой в работе и тревогами.
2. **«Расчистка участка»** (`lot_clearing`) — эталон ТЗ. Экскаватор работает весь день, самосвалов нет,
   и появляется отклонение «Возможное снижение темпа: экскаватор работает без самосвалов …» со снимками.
   Этап по плану отстаёт — нарочно.
3. **«Две пересекающиеся камеры»** (`dedup_demo`) — одна машина не считается дважды: у единицы
   техники две камеры, число машин совпадает с эталоном, а не с числом рамок.
4. **«Песчаный карьер»** (`kirov_quarry`) — экскаватор «работает», когда меняется поза стрелы, самосвал
   под погрузкой «стоит». Моточасы списываются из плановых («полоска» на вкладке «Техника»).
5. **Informatics Forum, Эдинбург** — три камеры одной стройки 2005–2008, модель Б проходит 8 этапов.
   Вердикт — отставание: сдача по плану 12.2007, по снимкам — 2008.
6. **Чикаго** — круглосуточная камера: ночные кадры идут в модель А, но не в модель Б.
7. **Камера** — плеер кадров со шкалой времени, слои рамок и маски, разбор кадра, калибровка по 4 точкам, зоны.
8. **«Проверить снимок»** — перетащить фото и получить рамки техники и этап за секунды. Здесь же
   переключение «локальные модели ⇄ внешний API».

Живая камера: `python -m simcam --folder <папка> --port 9101 --interval 30 --start-date 2026-09-25`.
Затем в UI создайте камеру-поток с адресом `http://127.0.0.1:9101` и нажмите «Подключить». Сервис сам
сообщит камере, куда слать кадры, и выдаст ей ключ (`POST /api/ingest`, заголовок `X-Camera-Key`).

## Тесты

```bash
python -m pytest -q                        # всё: ядро, бэкенд, статические проверки UI
python -m pytest -q tests/core             # модули ядра (без сети, GPU и torch)
python -m pytest -q tests/app              # бэкенд на фейковых модулях ядра
python -m pyflakes app core tools simcam tests   # pyflakes ставится отдельно: pip install pyflakes
```

Тесты не ходят в сеть. Внешние вызовы заменены фейками и кассетой реальных ответов GLM-4.6V
(`tests/fixtures/glm_cassette.json`). torch и ultralytics импортируются лениво, поэтому тесты ядра
не требуют ML-зависимостей. UI проверяется в браузере скриптами `tests/ui/shoot.py` и
`tests/ui/flows.py` (playwright в docker). `tools/ui_mock.py` поднимает интерфейс на записанных ответах
API без бэкенда.

## Команда и происхождение модулей

Сервис объединяет три ветки команды (ветка `egor-unified`, слияние — `docs/ARCHITECTURE.md` §2):

| Кто | Исходная ветка | Что вошло в СтройВзор |
|---|---|---|
| **Денис** | `dev-lamonifi` | Каркас FastAPI, камеры и поток кадров (`simcam`, `/api/ingest`, ключ камеры), динамическая маска фона (алгоритм перенесён в `core/stage/mask.py` вместе с замерами), модель Б на локальной VLM (`core/stage/checklist_vlm.py`), диаграмма Ганта план/факт, раскладка перечня работ (`reference/work_types*.csv`), `PLAN.md`, `AGENTS.md` |
| **Никита** | `api-solution` | Чек-лист признаков и словарь (`reference/checklist.json`, `work_map.csv`), скоринг этапов (`core/stage/scoring.py`), двухшаговый разбор GLM-4.6V и его промпты (`core/stage/checklist_vlm.py`, `prompts.py`, `core/vlm_client.py`), правила отклонений и хронология/прогноз (основа `core/analytics`) |
| **Егор** | `egor-unified` | Модель А (`core/equipment`: детектор, обучение на сервере, уточнение подтипа грузовиков, трекинг «работает/стоит», склейка камер, моточасы), контракты и архитектура, интеграция модулей, бэкенд и UI объединённого сервиса, демо-данные |

Исходники веток сохранены в истории git (слияния `a6a758d` и `23a646d`). Наследие, перенесённое в
`core/` (`api-solution/`, `app/pipeline/`), из дерева удалено.
