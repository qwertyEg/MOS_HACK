## 2. Архитектура

Кадр приходит одним из двух путей. **Поток** — камера-имитатор (`simcam/`) или настоящая камера шлёт кадры по одному на приёмник сервиса, с реальной меткой времени и своим ключом; это то, как система работает в жизни. **Папка** — прогон целиком, режим разработки: на нём мерялось качество маски, он повторяем. Оба пути ведут в один и тот же разбор.

```
      simcam (отдельный процесс, свой порт)
      или реальная камера на объекте
                     │  POST /api/ingest, ключ камеры
                     ▼
         ОЧЕРЕДЬ НА КАМЕРУ (одна, один поток)
         порядок кадров важен — маска зависит от предыдущих
                     │
            ФИЛЬТР ПРИГОДНОСТИ
            ночь / засвет / сбой камеры
                     │
         ┌───────────┴───────────┐
    ночной кадр              дневной кадр
         │                       │
         │              ДИНАМИЧЕСКАЯ МАСКА  ←──┐
         │              оператор красит фон    │
         │              один раз при заведении │
         │              камеры, дальше маска   │ обновление
         │              только сжимается       │ по календарным суткам
         │                       │             │
         ├───────────┬───────────┤             │
         │           │           │             │
     [МОДЕЛЬ А]   [МОДЕЛЬ А]  МОДЕЛЬ Б         │
     заглушка,    заглушка,   VLM, батч по     │
     не в потоке  не в потоке этапу, чек-лист  │
                              да / нет / не видно
                                 │             │
                    ключ → ответ, пишется в БД с кадром
                                 │             │
                                 └─────────────┘
                                 │
          СВЁРТКА ПО ОБЪЕКТУ: ПОДТВЕРЖДЁННЫЕ ВЕХИ
          сигналы этапов по порядку, соседние этапы перекрываются (§3.7)
                                 │
          ДИАГРАММА ГАНТА: ПЛАН / ФАКТ
          прогресс, вероятность срока и сдвиг в днях
                                 │
                              ДАШБОРД
```

Модель А — контракт зафиксирован (§4.3), **реализации нет**: `model_a_url` пуст, в потоке она не вызывается вовсе. Статусная машина техники и вердикт «работает/стоит» (§3.9–3.11) остаются методикой без кода. Для графика реализована предварительная эвристика вероятности срока; её калибровка на нескольких размеченных объектах остаётся открытой задачей (§3.8).

## 3. Методика — ядро проекта

### 3.1. Макроэтапы

| # | Макроэтап | Что сюда сворачивается из справочника |
|---|---|---|
| 1 | Подготовка территории | 10.x — снос, вырубка, вынос сетей, ограждение, бытгородок, геодезия |
| 2 | Ограждение котлована, шпунт, сваи | 12.3.5, 12.3.6, буронабивные и буроинъекционные сваи |
| 3 | Земляные работы, котлован | 12.3.7 — разработка грунта, выемка, обратная засыпка |
| 4 | Монолит подземной части | 12.3.1, 12.3.4, 12.3.9 — фундаментная плита, стены, колонны ниже нуля |
| 5 | Монолит надземной части | 12.4.4 — рост этажей |
| 6 | Кровля, фасад и остекление | устройство конструкций и пирога кровли; наружные стены, витражи, окна |
| 7 | Благоустройство | 12.7.x — проезды, озеленение, МАФы, ограждение территории |

**Кровля и фасад — один этап, а не два.** Разделение технологически верное,
но с камеры неподтверждаемое: у высокого здания кровля в кадр почти не
попадает, и на вопрос «готова ли кровля» по снимку не ответить. Фасад виден
всегда и идёт с кровлей практически одновременно. Отдельный этап, который
наблюдением не закрыть, — это этап, на котором граница прогресса встанет
навсегда, поэтому вместо двух этапов заведён один, и опознаётся он по фасаду.

**Башенный кран отдельным этапом не делаем.** Его нет в справочнике как вида работ, он стоит месяцами и перекрывает этапы 4–7 сразу, а на фотоотчётах видно, что появляется он ещё на нулевом цикле. Вместо этапа — атрибут состояния площадки `tower_crane_present` с датой первого появления.

### 3.2. Уровень агрегации: измеряем по корпусам, отчитываемся по объекту

Организаторы ответили прямо: интересуют сроки этапов **всего объекта**. Это разворот относительно предыдущей версии плана, где планирование сидело на корпусе.

При этом физически измерять «этажность объекта из трёх корпусов» нельзя — это три разных числа. Поэтому разводим два понятия:

- **корпус — внутренняя единица измерения.** Прогресс, этажность, признаки этапа считаются по корпусу там, где корпуса различимы.
- **объект — единица отчётности.** Вердикт, календарный план, прогноз задержки, дашборд — только на уровне объекта.

**Правила свёртки корпусов в объект:**

| Величина | Правило |
|---|---|
| Этап начался | как только начался **хотя бы на одном** корпусе |
| Этап завершён | когда завершён **на всех** корпусах |
| Прогресс этапа | средневзвешенное по корпусам, **вес = площадь корпуса** из декларации |
| Дата завершения этапа | максимум по корпусам |
| Вердикт | по худшему корпусу на критическом пути |
| Прогноз ввода | по самому позднему корпусу |

Вес по площади важен: корпус на 33 этажа и пристройка на 2 этажа не могут весить одинаково. Площади берутся из проектной декларации.

**Рекомендация по объёму работ: разделение на корпуса делаем необязательным.**

Базовый режим — **без корпусов вообще**. Вся маскированная область считается одним объектом, модель Б отвечает на вопросы по всей области, мультилейбл естественно ловит параллельные этапы: если один корпус в котловане, а другой на монолите, чек-лист даёт «да» обоим этапам, и оба этапа активны на объекте. **Это ровно та картина, которую организаторы и просят.** Ручной настройки — ноль.

Расширенный режим — оператор дополнительно размечает зоны корпусов, получает детализацию и более точный счёт этажей.

Для соло-разработки это принципиально: обязательный путь не требует настройки вообще, а зоны корпусов уезжают в «желательно».

### 3.3. Входной фильтр кадров

#### 3.3.0. Ракурсы и что с них измеримо

Организаторы подтвердили: есть и периметральные камеры, и вид сверху с мачты. Разные ракурсы дают разные величины, и это надо учитывать при агрегации.

| Ракурс | Хорошо измеряется | Плохо или никак |
|---|---|---|
| Сбоку, с земли | этажность, фасад, техника | площадь котлована, благоустройство |
| Сверху, с мачты | котлован, площадь плиты, зоны, благоустройство, расстановка техники | этажность (ракурс сверху её скрывает) |
| С соседнего дома, высоко | общий план, состав техники, все этапы обзорно | детали, мелкая техника |

Отсюда поле `view_type` у камеры и правило: измерение берётся с той камеры, для которой оно помечено как надёжное. Этажность не считаем с верхнего ракурса, площадь котлована не считаем с бокового.

#### 3.3.1. Ночные кадры

Работы ночью идут — организаторы подтвердили. Но в модель Б ночные кадры не отдаём.

Причина следует из метода динамической маски (§3.4): ночной кадр снят в ИК или в другом цветовом режиме, у него принципиально другая статистика яркости и шума. Смешивание дневных и ночных кадров в одной медиане разрушает разделение статики и динамики — половина кадров будет «отличаться» от другой половины просто из-за режима съёмки, и вся сцена прочитается как динамическая.

**Правило разделения:**

```
МОДЕЛЬ А  —  работает ВСЕГДА, день и ночь.
             Техника работает круглосуточно, детекция должна быть круглосуточной:
             движется / стоит, активные часы, простои — всё считается и ночью.

МОДЕЛЬ Б  —  только дневные кадры.
             Ночные кадры могут только ухудшить ответ, ими пренебрегаем.

МАСКА     —  только дневные кадры (иначе рушится медиана).
```

Следствие для §3.8: активные дни считаются по выходу модели А, **то есть включая ночные смены**. Если бы ночь выпала из подсчёта, коэффициент простоя `k_idle` оказался бы завышен, а прогноз — пессимистичным без причины.

Разделение дня и ночи — по времени восхода/заката для координат объекта плюс проверка на насыщенность кадра (ИК-режим даёт почти монохром).

#### 3.3.2. Прочие негодные кадры

Отсекаются до всех моделей: засвет, полная тьма при выключенном ИК, залитый дождём или заснеженный объектив, зависший кадр (полное совпадение с предыдущим), артефакты сжатия. Проверки простые — яркость, контраст, доля насыщенных пикселей, pHash с предыдущим кадром. Отброшенные кадры логируются: доля негодных кадров сама по себе метрика здоровья камеры, и её стоит показывать.

### 3.4. Динамическая маска фона

**Метод изменился с первой версии плана.** Полностью автоматический вариант — маска, собранная из истории камеры без участия оператора, — на реальных данных Эдинбурга сходился ненадёжно: без стартовой подсказки алгоритм либо схлопывался к маске в 6% кадра, либо расползался до 100%, в зависимости от параметра. Заменён на гибридный: **оператор один раз красит фон, дальше маска только сжимается**. Полная реализация и вся история измерений — `app/pipeline/mask.py`, докстринг модуля держит числа всех отвергнутых вариантов; здесь — методика.

#### 3.4.1. Идея — оператор задаёт старт, алгоритм только сжимает

Маска — область **фона**: то, что скрывается от модели Б (соседние готовые дома, дорога, забор, горизонт). Всё незакрашенное — наш объект.

**Начальное условие задаёт человек, не алгоритм.** При заведении камеры оператор получает первый кадр и один раз закрашивает фон кистью в браузере. Это разом снимает два ограничения, из-за которых чисто автоматический вариант не работал:

- не нужно ждать недели, пока маска накопит достаточно истории и сойдётся — она рабочая с первого кадра;
- неважно, что на момент установки камеры уже стоят пять этажей — они не станут фоном по ошибке, потому что фон не выводится из наблюдений, а указывается прямо.

**Дальше маска только сжимается, никогда не растёт.** Здание растёт вверх и заползает на закрашенную область — фона становится меньше; обратное физически невозможно. Направление монотонности выбрано по цене ошибки:

```
маска растёт     →  в пределе скрыто всё, объект не виден, разбор сорван
маска сжимается  →  в пределе не скрыто ничего — откат к полному кадру,
                    хуже, чем работа вовсе без маски, стать не может
```

Ошибки оператора тоже ведут себя прилично: закрасил лишнего, задев стройку, — стройка меняется, алгоритм сам откроет эту область; закрасил мало — часть фона останется видимой, что не хуже работы совсем без маски.

#### 3.4.2. Почему это работает

Определение не изменилось, только источник: **наш объект — это то, что оператор не пометил фоном на старте, минус то, что перестало отличаться от фона за время наблюдения.** Пиксель, ни разу не показавший устойчивого изменения, остаётся закрашенным навсегда; здание, достроенное три месяца назад, из маски не возвращается — это и есть фиксация истории, см. §3.4.3.

#### 3.4.2а. Принцип достаточности: отсекаем только спутываемое

Решение не изменилось и по-прежнему держит объём работы: **маска обязана отсекать только то, что модель Б может спутать с нашим объектом.** Всё остальное можно оставить в кадре — это не ошибка, а экономия.

Спутываемо: соседние построенные здания, чужая активная стройка, строительные конструкции за пределами площадки. Не спутываемо: небо, облака, лес, дорога, транспорт на ней, пешеходы, горизонт — в чек-листе нет ни одного вопроса, ответ на который зависел бы от погоды или листвы, модель Б заполнит его одинаково при любом небе. Отдельный детектор неба по-прежнему не нужен — но не потому, что небо «само» попадает в видимую область через слой текущей динамики (такого слоя в реализации больше нет, см. ниже), а потому, что **оператор просто не красит небо как фон**, если оно ему не мешает.

#### 3.4.3. Алгоритм

Состояние на камеру (`MaskState`, `app/pipeline/mask.py`):

```
background    bool    закрашенный оператором фон — только убывает
evidence      int16   по клеткам: счётчик подряд идущих окон с изменением
hot_count     int32   по клеткам: сколько раз клетка вообще мелькала
initial_area  int     площадь исходной маски — для «маски цело, %»
```

Обновление — **по календарным суткам**, не по кадрам (на датасете с одним кадром в день разницы нет, при реальном темпе в 20 минут — есть), окно `WINDOW_DAYS = 10` дней:

1. **Отбор кадров.** Только дневные, только годные (§3.3), по одному-два на день, **в один и тот же час** — иначе тени от солнца поедут и дадут ложную динамику.
2. **Приведение.** Уменьшаем до `WORK_WIDTH = 480` px по ширине, в оттенки серого, лёгкое размытие — маска нужна грубая, шум на мелком масштабе только мешает.
3. **Оценка изменения клетки.** **Разность медиан половин окна**, а не разброс внутри окна (`CELL = 16` px клетка).

   > **Поправка, найденная на замере.** Естественная первая реализация — медианное абсолютное отклонение (MAD) по окну: устойчива к одиночному грузовику или прошедшему человеку. Но строительство — это последовательность ступенек (точка была небом, стала стеной и дальше не меняется), и если ступенька легла не ровно на середину окна, медиана равна большинству, а MAD — около нуля. На синтетической сцене рост этажа детектировался **в одном окне из трёх**, остальные MAD пропускал.
   >
   > Рабочая формула: `изменение = |median(вторая половина окна) − median(первая половина)|`. Устойчивость к транспорту и людям сохраняется (медиана внутри каждой половины их гасит), ступенька видна во всех окнах, где она вообще попадает в окно.
4. **Сравнение по яркости, не по структуре** — измерено на 319 кадрах Edinburgh Informatics Forum. Клеточные гистограммы градиента дают лучшее сырое разделение (3.31× против 2.14×), но в сквозном тесте проигрывают: F1 0.67 против 0.86 у яркости. Отрезки Хафа проигрывают разгромно — F1 0.10, сигнала почти нет. Причина: фон здесь — деревья и перепаханная земля, не оконные сетки со стабильной геометрией. На целевом сценарии (соседние жилые дома) структурный признак может выиграть, но переключать без нового замера нельзя.
5. **Якорная нормировка освещения.** Общий сдвиг яркости кадра (пасмурно, снег, смена сезона) вычитается по самым спокойным ещё закрашенным клеткам, не по всей маске — иначе, когда здание отвоюет её большую часть, опора сама начинает измерять стройку. Замерено: F1 0.39→0.42 и 0.73→0.80 на двух прогонах, от исходной маски доживает на 13 и 5 п.п. больше.
6. Порог → бинарная карта изменения → `evidence` растёт для изменившихся клеток, падает для неизменившихся.
7. Клетка стирается из `background` (`background = False`, то есть открывается модели) после `LOCK_WINDOWS = 3` окон подряд с изменением. Разовый всплеск — грузовик за забором на неделю — откатывается назад и не фиксируется.
8. `background` **никогда не растёт**, только теряет клетки.

**Проверено и отвергнуто** (числа — на двух реальных прогонах разом, покупка точности на одном ценой другого): отложенное подтверждение стирания по обратимости (0.27→0.31 на трудном прогоне, но 0.80→0.72 на удачном); требование связности растущей области снизу вверх (0.80→0.60); отбрасывание одиночных клеток (0.80→0.53).

**Чего яркость не умеет — измерено, не гипотеза.** На прогоне, где стройка занимает лишь пятую часть закрашенного, точность упирается в 0.33 при любом пороге: 71% фоновых клеток хоть раз дают вспышку изменения длиной в три окна — снег, мокрый асфальт, переставленный контейнер, техника у границы площадки. Разумный следующий шаг, **не реализован**: право оператора пометить область как **неприкосновенную** — там, где он уверен, гарантия нужнее эвристики.

**Не реализовано и снято относительно первой версии плана.** Фильтр смежности (новая динамичная область обязана касаться уже зафиксированного объекта) и ограничение площади прироста за окно («небо как мост») были задуманы для автоматического варианта, где маска росла из пустого состояния и без них расползалась на чужую активную стройку рядом. При переходе на оператор-заданный старт необходимость снизилась — оператор и так не красит чужую стройку как объект, — и обе идеи не были закодированы. Если демо покажет расползание маски через касание с посторонней динамикой, это первое, что стоит достать с полки.

#### 3.4.4. Сильные и слабые стороны — обновлено под текущий метод

**Сильные:**

| Плюс | Почему важно |
|---|---|
| **Холодный старт решён, а не смягчён** | Маска рабочая с первого кадра — оператор задал её сразу, недели истории ждать не нужно |
| **Наблюдение не с нуля стройки — больше не проблема** | Камеру повесили, когда уже стоят пять этажей, — они не станут фоном по ошибке, потому что фон не выводится из истории |
| Монотонность физически верна | Здание не разбирается обратно, маска только сжимается — модель совпадает с реальностью |
| Ошибки оператора самоисправляются или безвредны | Закрасил лишнего — стройка сама откроет; закрасил мало — не хуже работы без маски |
| Якорная нормировка держит сезонность | Снег и смена освещения не читаются как стройка, измерено §3.4.3 п.5 |

**Слабые, честно:**

| Минус | Насколько опасно | Что делаем |
|---|---|---|
| Ручная разметка на старте всё же есть | Низко | Один клик на камеру, не на кадр; закрасить лишнего не страшно |
| Сцены, где фон «возбудим» (снег, техника у границы) | Высоко на таких сценах | Точность упирается в 0.33 при любом пороге — измерено. Лечится защищённой зоной оператора, **не реализовано** |
| Перестановка камеры | Открытый вопрос | Гомография из первой версии плана **не реализована**. Сейчас — ручной сброс и перерисовка, §3.4.6 |
| Чужая активная стройка вплотную | Средне | Фильтр смежности **не реализован** — единственная защита сейчас: не закрашивать чужую стройку как объект на старте |
| Тени от солнца ползут по фасадам | Средне | Выборка строго в один и тот же час |
| Сезонность — снег, листва | Средне | Якорная нормировка + длинное окно, но не снимается полностью |
| Ночь ломает статистику | Решено | Ночные кадры в расчёт маски не входят, §3.3.1 |
| Как закраска влияет на VLM | Измерено частично | §3.4.5 |

Детекция смены ракурса по опорным точкам (ORB) и перепривязка маски гомографией, описанные в первой версии плана, не закодированы — в `app/pipeline/` нет такого модуля. Сегодняшний путь при физическом сдвиге камеры — вручную сбросить состояние (`POST /cameras/{id}/reset-mask`) и перерисовать заново; накопленная история теряется. Стоит вернуться к этому, если демо-камеру можно случайно задеть; при работе с симулятором риска нет вовсе.

### 3.5. Чек-лист этапа — тернарный, ключ-ориентированный

Формат из первой версии плана — блок `must_have`/`must_not_have`/`questions`, встроенный под конкретный этап, — заменён на **общий пул вопросов с ключами**. Причина: один и тот же признак («видно ли здание выше уровня земли») нужен нескольким этапам сразу — спрашивать его заново под каждый смысла нет, ответ на кадр один.

**Источник — три CSV в `reference/`, не код:**

- `checklist_questions.csv` — общий пул наблюдаемых признаков: `key, latching, text, hint`. `latching` — может ли признак, однажды став «да», больше никогда не вернуться в «нет» (закрытая кровля видна всегда; сваебойная установка — временный признак, уезжает с площадки). `hint` — «как выглядит», подсказка для VLM, добавляется отдельной фразой в промпт: без неё модель отвечает по названию признака, а не по картинке.
- `stage_questions.csv` — привязка `key → stage` с полярностью: `must_have` (характерно для этапа), `must_not_have`, `context` (общий фон, в счёт этапа не идёт). В текущем справочнике оставлено по пять `must_have` на этап, чтобы чек-листы были сопоставимы по размеру; активная логика переходов их количество не сравнивает.
- `stages.csv` — семь макроэтапов, §3.1.

`SiteStage.questions` в БД — **снимок** состава на момент сохранения плана объекта. Правка справочника не должна задним числом менять вопросы у объекта, который наблюдается месяцами: иначе половина истории окажется по одному набору, половина по другому.

**Ответ по-прежнему тернарный: да / нет / не видно** («не видно», а не «не уверена» — конкретная инструкция исполняется заметно лучше размытой). Вопросы одного этапа идут **одним запросом, батчем 4–6, с жёсткой JSON-схемой** (`response_format: json_schema` — каждый ключ обязательное поле с перечислением значений, лишние запрещены; разбор сводится к `json.loads`). Замер: 26 вопросов поодиночке 13.9 с, тем же батчем 6.8 с (Ollama переиспользует KV-кэш картинки), но батч всеми 36 сразу заметно врёт — на фасадном кадре получили 21 «нет» из 26 там, где верно было «не видно». Группа 4–6 — компромисс, подтверждённый замером, единица батча — чек-лист одного этапа.

Облачные эндпоинты поддерживают ограничение ответа схемой не все — откат `json_schema → json_object → свободный текст`, режим настраивается за профиль в `/settings`, §4.2 и §6.

```jsonc
// checklist_questions.csv, одна строка пула
{"key": "pile_rig", "latching": false,
 "text": "Видна ли сваебойная или буровая установка — машина с высокой вертикальной мачтой?",
 "hint": "мачта выше кабины в несколько раз, шнек или молот"}

// stage_questions.csv — тот же ключ привязан к этапу 2 с полярностью must_have
```

### 3.6. Измеримые величины прогресса

| # | Этап | Величина | Знаменатель | Ракурс |
|---|---|---|---|---|
| 1 | Подготовка | доля площадки освобождена и огорожена | вся маска | верхний |
| 2 | Шпунт, сваи | число погружённых свай | проект (вводится) | любой |
| 3 | Котлован | площадь и глубина выемки | проект | **верхний** |
| 4 | Монолит подземной | доля забетонированной плиты | пятно застройки | **верхний** |
| 5 | **Монолит надземной** | **номер текущего этажа** | **этажность из декларации** | **боковой** |
| 6 | Кровля, фасад и остекление | доля закрытого фасада | площадь фасада | боковой |
| 7 | Благоустройство | доля благоустроенной площади | площадь двора | верхний |

**Этаж — якорь методики.** Величина дискретная, считаемая, знаменатель берётся прямо из проектной декларации. Единственная метрика, дающая абсолютный процент без допущений, и стоит она на самом длинном и критичном этапе. Мерить только с боковых камер — с мачты этажность не видна.

#### Как считаем этажность: верхняя граница маски

Спрашивать у модели Б «сколько этажей» напрямую — ненадёжно, VLM плохо считают повторяющиеся элементы. Но нам и не нужен абсолютный счёт: **сама маска — измерительный прибор.** Здание растёт вверх, вместе с ним поднимается верхняя граница незакрашенной области. Её высота в пикселях (`CameraState.mask_top_edge_px`) — готовая кривая прогресса этапа 5, побочный продукт маски.

```
mask_top_edge_px(t)  →  кривая роста  →  темп в §3.8
```

Перевод пикселей в этажи — через шаг этажа (`px_per_floor`): как только два перекрытия подряд отработаны, известно, сколько пикселей приходится на этаж.

**Статус: измеряется, но не используется в выводе об этапах.** `mask_top_edge_px` и `px_per_floor` — поля в модели `CameraState`, копятся и показываются оператору на странице камеры («верхняя граница»). Перевод в номер этажа и подключение этой кривой к §3.7 не сделаны — сегодня вывод об этапах целиком идёт по ответам чек-листа модели Б (`above_grade`, `formwork_floor` и т.п.), верхняя граница маски участвует только как показатель для оператора, не как сигнал для системы.

Оговорка на будущее: работает на боковом ракурсе и при неизменном положении камеры. При перестановке камеры (§3.4.6, не реализовано) шаг этажа пришлось бы пересчитывать заново.

### 3.7. Как определяем начало и прогресс этапов

Ответы камер за день сводятся по ключу: «да», если это увидела хотя бы одна камера; иначе «нет», если хотя бы одна камера смогла признак оценить; иначе «не видно». Камера, которая не смотрит на объект, не отменяет наблюдение другого ракурса.

Этапы не конкурируют за единственное место на объекте. Каждый начинается по своему физическому событию, подтверждённому минимум двумя положительными днями в пределах недели. Кандидатом служит только следующий этап по порядку плана, поэтому случайный сигнал благоустройства не перепрыгнет через котлован. После подтверждения начала следующего этапа предыдущая полоса сохраняется ещё 14 дней: это окно показывает нормальную параллельность соседних работ. Дыры в наблюдениях длиннее 10 дней разрывают фактический отрезок.

Опорные сигналы переходов для строительного объекта:

| Переход | Подтверждающий признак |
|---|---|
| Подготовка → сваи | сваебойная/буровая установка, сваи или шпунт |
| Сваи → котлован | большая открытая выемка на значительной части пятна здания; отдельные свайные ямы и траншеи исключены |
| Котлован → подземная часть | видимый бетон на дне/в конструкциях котлована или стены подземной части; резерв — совместная опалубка подземной части и арматура. Песок и щебень сами по себе границу не двигают |
| Подземная → надземная часть | первый различимый этаж именно этого здания выше земли |
| Надземная часть → кровля/фасад | начались окна, утепление или облицовка |
| Кровля/фасад → благоустройство | дорожки, покрытие или озеленение внутри границы участка; отсутствие техники само по себе не сигнал этапа |

Общие слова о «признаках идущей стройки» и строительный мусор не участвуют в
чек-листе этапов: они встречаются на нескольких стадиях и не различают ход
работ. Для техники используются отдельные наблюдения: сваебойная/буровая
установка и активный экскаватор, автобетононасос и автобетоносмеситель у зоны
заливки, башенный кран при строительстве каркаса и фасада. Наличие техники
остаётся подтверждением работ, но не единственным условием перехода. Прогресс
благоустройства считается по видимым работам и готовым результатам; «техники
не видно» не увеличивает процент.

Точные проценты модель Б не угадывает. В `app/pipeline/progress.py` заданы видимые вехи с весами внутри этапа. Завершённая веха даёт полный вес; активный сейчас временный признак — половину. Отдельно считается покрытие наблюдениями: доля веса тех вех, на которые камеры дали «да» или «нет». Один и тот же расчёт даёт прогресс и качество наблюдений каждого этапа. Общий прогресс объекта — взвешенная сумма процентов этапов; веса этапов по умолчанию (5, 8, 7, 12, 35, 23, 10) отражают объём работ и редактируются на странице плана для конкретного объекта.

Ответы по старой формулировке не смешиваются с новой: агрегатор сопоставляет сохранённый текст вопроса с текущим снимком чек-листа этапа. После правки CSV нужно обновить шаблоны и снимок плана, затем повторно прогнать кадры, чтобы получить полную сопоставимую историю.

Диаграмма показывает факт по объекту целиком, с двумя полосами — календарный план и камеры. Для каждого этапа отображаются зелёная шкала прогресса, полнота наблюдений, предварительная эвристика вероятности завершить этап в срок и отклонение от планового прогресса в днях. Высота строки фиксирована. Вероятность пока не калибрована на серии независимых объектов и подписана как предварительная оценка.

### 3.8. Предварительная оценка срока

**Статус: предварительная эвристика реализована в карточке объекта; статистически калиброванного прогноза пока нет.** Для активного этапа темп берётся из накопленного процента вех, оставшаяся работа экстраполируется по времени от фактического начала. Разница прогнозной даты с плановым сроком переводится в ограниченную сигмоидальную оценку от 1% до 99%; результат показывается с полнотой наблюдений. Для этапа, за которым подтверждён следующий, исход рассчитывается по концу его фактической полосы с учётом 14-дневного перекрытия. Это оценка, а не независимо измеренная дата завершения: на одном объекте она не калибрована и не является подтверждённой вероятностью.

Отклонение в днях для текущего этапа получается переводом разницы между фактическим и линейным плановым процентом в календарные дни длительности этапа. Положительное значение означает опережение, отрицательное — отставание. Старая мера пересечения плана и факта удалена из интерфейса.

#### Уровень 1. Три оценки темпа

- `v_recent` — по окну 14 дней;
- `v_overall` — с начала этапа;
- `v_plan` — из календарного плана.

Прогноз выдаём интервалом, не точкой: оптимистичный по `max(v_recent, v_overall)`, базовый по взвешенному (0.6 свежести / 0.4 истории), пессимистичный по `v_recent`, если он ниже среднего.

#### Уровень 2. Темп в активных днях, а не в календарных

Ядро методики.

Организаторы потребовали два отдельных вывода — «работает или стоит» и «предсказывай задержку». **Мы связываем их в одну формулу:**

```
v_active = Δпрогресс / число активных дней в окне
k_idle   = календарные дни / активные дни

прогноз = (100% − прогресс) / v_active × k_idle
```

Это различает два случая, которые линейная экстраполяция путает: этап отстаёт из-за двухнедельного дождя (темп работы нормальный, отставание перестанет расти) против этап отстаёт при полной загрузке (темп реально низкий, будет накапливаться). Мы не только называем задержку, но и говорим причину.

Активные дни считаются **включая ночные смены** — §3.3.1.

#### Уровень 3. Поправка на нелинейность

Начало этапа (развёртывание, завоз, первые захватки) и хвост (доводка, примыкания, исправления) идут медленнее середины. Фитить логистику на 10–15 точках опасно. Компромисс: линейная экстраполяция по активным дням плюс табличный коэффициент на фазу этапа, последние 15% с коэффициентом ≈1.4–1.6. Калибруем по фотоотчётам, не выдумываем.

#### Уровень 4. Каскад по цепочке этапов

- у каждой пары этапов `lag` — допустимое наложение (монолит надземной части стартует при 80% подземной, а не при 100%);
- флаг `on_critical_path` — благоустройство нагоняется, монолит нет;
- сдвиг передаётся дальше с коэффициентом поглощения, зависящим от запаса между плановым концом N и стартом N+1.

Итог — прогнозная дата ввода объекта.

#### Уровень 5. Ранние предупреждения, до просадки прогресса

Главная бизнес-метрика — lead time, и берётся он отсюда, а не из экстраполяции.

| Индикатор | Порог | Что означает |
|---|---|---|
| `STAGE_NOT_STARTED` | этап должен был начаться N дней назад, признаков нет | самый ранний и надёжный сигнал |
| `ACTIVITY_DROP` | доля активных дней за 14 дней ниже исторической медианы | лидирующий индикатор |
| `EQUIPMENT_MISSING` | требуемой **задействованной** техники нет X дней | темп просядет через неделю |
| `EQUIPMENT_PARKED_ONLY` | техника этапа присутствует, но вся в статусе PARKED | **работы встали, хотя техника в кадре** |
| `CREW_SHRINK` | среднее число рабочих падает трендом | бригаду снимают с объекта |
| `TEMPO_DECAY` | `v_recent` < 0.7 × `v_overall` | темп ухудшается внутри этапа |

`EQUIPMENT_PARKED_ONLY` — прямое следствие ответа организаторов про технику в ожидании вывоза. Без различения статусов этот случай выглядел бы как нормальная работа.

#### Уровень 6. Нормативы темпа из открытых данных

Холодный старт: первые недели своей истории нет. Решение — таблица `stage_norms`, собранная заранее:

| Источник | Что даёт |
|---|---|
| Фотоотчёты наш.дом.рф по 10–20 объектам | реальные длительности этапов, «дней на этаж» |
| П.17 деклараций | плановые длительности, разброс по типам объектов |
| Наш CCTV-датасет | доля активных дней, суточный и недельный профиль |

Пока истории мало, прогноз идёт на нормативе, дальше вес смещается на собственные наблюдения.

#### Формат выдачи

```
Объект «Кавказский бульвар, 51» · Этап 5 «Монолит надземной части»
  План:            01.06.2026 – 15.03.2027
  Прогноз:         02.04.2027   (+18 дней)
  Диапазон:        25.03 – 20.04
  Прогресс:        57%   (корпус 3.4: 19/33 эт.; 3.5: 14/33; 3.6: 9/24)

```

#### Оценка самого прогноза

Бэктестинг на фотоотчётах наш.дом.рф: обрезаем историю на 30 / 50 / 70%, строим прогноз, сравниваем с фактом. Метрика — MAE прогнозной даты в днях на каждом горизонте. **Отдельный сильный слайд:** мало кто покажет, что прогноз проверен, а не нарисован.

### 3.9. Техника: присутствует ≠ задействована

Организаторы: техника часто стоит на площадке неделями в ожидании вывоза, потому что возить туда-сюда дороже. Это ломает наивную логику «экскаватор в кадре ⇒ земляные работы идут».

**Статусная машина единицы техники:**

| Статус | Условие | Как учитывается |
|---|---|---|
| `ACTIVE` | сместилась между кадрами или изменила позу | считается в `equipment_expected`, день активный |
| `IDLE` | не двигалась до 1 рабочей смены | считается присутствующей, простой короткий |
| `PARKED` | не двигалась N дней **и** дисперсия позиции около нуля | **не считается в соответствии этапу, не порождает аномалий** |
| `DEPARTED` | отсутствует M кадров подряд | снята с учёта |

Порог перехода в `PARKED` — порядка 2–3 суток; настраивается.

Что это меняет:

- в чек-листе этапа `equipment_expected` засчитывается **только `ACTIVE`**;
- `PARKED`-техника не поднимает аномалию «лишняя техника» — она просто ждёт вывоза;
- появляется новый, более полезный сигнал `EQUIPMENT_PARKED_ONLY`: техника нужного этапа есть, но вся припаркована — значит работы встали, хотя визуально площадка выглядит укомплектованной.

Дополнительно: оператор может разметить **зону отстоя** (`zone_type = 'parking'`), техника в ней по умолчанию не участвует в сопоставлении с этапом.

### 3.10. «Работает или стоит»

Метод подсказали сами организаторы: техника работает, если сместилась между кадрами с интервалом 20 минут.

- сопоставляем детекции соседних кадров одной камеры по классу и расстоянию центров;
- смещение больше порога → `ACTIVE`; нет смещения → отсчёт к `IDLE` и далее к `PARKED`;
- агрегат по дню → признак «день активный», питающий §3.8 уровень 2;
- **ночные кадры участвуют** — работы ночью идут.

**Честное ограничение:** экскаватор может работать, не перемещая шасси. Частично лечится учётом изменения формы bbox при неизменном центре (стрела движется), полностью — нет. В «Условия и ограничения».

### 3.11. Аномалии

- задействованная техника, которой нет в `equipment_expected` текущего этапа → лишняя техника;
- техника вне своей зоны (кроме зоны отстоя) → нарушение зонирования;
- ни одной активной единицы и ни одного рабочего N дней подряд → простой площадки;
- признаки этапа, который по плану давно завершён или ещё не начат → рассинхрон с планом;
- вся техника этапа в статусе `PARKED` → §3.8 уровень 5.

### 4.2. Модель Б

Модель **не в репозитории**, подключается по конфигурации:

```env
VLM_BASE_URL=http://localhost:11435/v1
VLM_API_KEY=<случайный ключ, не менее 32 символов>
VLM_MODEL=qwen3-vl:30b-a3b-instruct
VLM_TIMEOUT=120
VLM_TEMPERATURE=0
```

> На DGX локальный Ollama-контейнер доступен с хоста только через `127.0.0.1:11436`. Bearer-прокси проекта слушает порт 11435 и отклоняет запрос без `VLM_API_KEY`; Ollama сама локальную авторизацию не проверяет. Для внешнего доступа нужен TLS reverse proxy, например `https://home.udron.ru/ollama`, который пересылает заголовок Authorization.

Протокол — OpenAI-совместимый `/chat/completions` с картинкой в `image_url` (data-URI). Подойдёт Ollama, vLLM, llama.cpp, облачный эндпоинт.

**Тег изменён относительно первой версии плана: `qwen3-vl:30b-a3b-instruct`, не голый `qwen3-vl:30b`.** Без суффикса Ollama подтягивает **thinking-версию**, которая перед каждым ответом генерирует развёрнутую цепочку рассуждений — для тернарного вопроса чек-листа это чистый проигрыш: латентность растёт в разы, а при недостаточном бюджете токенов рассуждение съедает его целиком и ответ приходит пустым (`finish_reason: length`), что раньше тихо утекало в поштучный опрос и растягивало разбор с минут до часов. Явный `-instruct`-вариант рассуждения не генерирует.

**Провайдер модели Б переключается в интерфейсе, а не только в `.env`.** `/settings` — таблица профилей (`VlmProfile` в БД): адрес, модель, ключ, режим ограничения ответа (`json_schema` / `json_object` / свободный текст). Активный профиль читается из БД на каждое создание клиента, то есть переключение действует со следующего кадра без перезапуска сервиса. Заготовки — локальная Ollama, GLM (Zhipu), OpenRouter, OpenAI; адреса и названия моделей правятся в интерфейсе, не в коде — провайдеры переименовывают модели чаще, чем выходят релизы сервиса. Облачные эндпоинты поддерживают ограничение ответа JSON-схемой не все — конвейер откатывается `json_schema → json_object → свободный текст` по цепочке, а не сразу в поштучный опрос. Кнопка «Проверить» бьёт настоящим вопросом по настоящему кадру из базы, а не `GET /models`: последний отвечает и у эндпоинта, не умеющего ни картинок, ни схемы.

**Правило вызова: не чаще раза в час отснятого времени** (`settings.live_model_b_hours`, throttle по метке кадра, не по настенным часам — при ускоренном показе архива сутки съёмки проходят за минуты). «Лучший кадр по освещённости» и «внеочередной вызов при существенном изменении маски» из первой версии плана — задумка, не реализована; сегодня правило проще: раз в час, и точка.

### 4.4. Календарный план — конкретные даты, дд/мм/гггг

Организаторы: **даты конкретные, не кварталы.** Реализовано так, как задумано, с одним отличием от первой версии плана — вход через проектную декларацию не строился (см. ниже). Два входа, не три:

1. **Ручной ввод** в конфигураторе объекта — базовый, работает всегда. Поля дат — текстовые дд/мм/гггг со встроенным календарём (`app/static/dates.js`): штатный `<input type="date">` не годится, его формат зависит от языка браузера и из разметки не задаётся.
2. **Загрузка файла плана** (CSV или обычный текст, `app/plan_import.py`) — строки вида `Название этапа: дд.мм.гггг - дд.мм.гггг`. Разбор терпимый: даты и день-первым, и ISO; названия сопоставляются со справочником точно и нечётко — по словам, не более одной опечатки в слове от пяти букв (`difflib` по общей похожести строк склеивал «подземной» с «надземной», пришлось написать своё сравнение); отчёт о применённых, добавленных и нераспознанных строках с номерами показывается один раз через сессию.

**Третий вход из первой версии плана — загрузка проектной декларации PDF с regex-разбором и черновым предзаполнением по кварталам — не реализован.** `tools/parse_declaration.py` не существует, поле `declarations` в БД не заполняется никаким кодом. Демо-план вместо этого построен вручную по реальным меткам времени датасета `data/raw_noon_images/` (`data/plan_for_raw_noon_images.txt`) — см. §7.

**«Сегодня» для объекта** (`Site.sim_today`) — по умолчанию не настенное время сервера, а дата **последнего принятого кадра**: у камеры своя метка времени в имени файла, и красная черта на диаграмме Ганта сама двигается вправо по мере съёмки. Ручная дата — кнопка «Указать» под диаграммой, только для отмотки назад при разборе; добавлена по прямому запросу для эксперимента с историческим датасетом, где настенные часы к происходящему на кадрах отношения не имеют.

Таблица «% готовности → активные макроэтапы» ниже — часть нереализованного пути 3 (предзаполнение по вехам декларации), оставлена как справка на случай, если парсер декларации всё же понадобится:

| % готовности | активные макроэтапы |
|---|---|
| 0–20% | подготовка, шпунт/сваи, котлован |
| 20–40% | монолит подземной, старт надземной |
| 40–60% | монолит надземной |
| 60–80% | завершение монолита, кровля, старт фасада |
| 80–100% | фасад, благоустройство |

### 4.5. Технические решения

| Решение | Выбор | Почему |
|---|---|---|
| Фронтенд | Jinja2 + HTMX + Tailwind CDN | соло; ноль сборки, один сервис вместо двух |
| Миграции | `models.py` + идемпотентные `ALTER ... IF NOT EXISTS` (`db.DRIFT`) при старте | отдельный `schema.sql` заведён не был: `Base.metadata.create_all` создаёт недостающие таблицы, `ensure_columns()` довешивает колонки на уже существующие — дешевле отдельного инструмента миграций на хакатон |
| Фоновая обработка | поток на очередь (`threading.Thread`), одна очередь на камеру | не о том, чтобы не блокировать event loop, а о порядке: маска копится последовательно, кадр камеры N+1 не может разбираться раньше кадра N |
| **Хранение кадров** | **MinIO (S3-совместимый)** | отдельный сервис и том: приложение можно пересобрать, кадры останутся. Организатор подставит свой S3 сменой `S3_ENDPOINT`. Presigned URL отдают миниатюры минуя бэкенд |
| CV-обвязка | OpenCV | маска, морфология — всё там |
| БД | Postgres | требование задачи |

BLOB в Postgres — нет: дамп раздувается до десятков гигабайт. В БД только ключ объекта, размеры, время, хеш. В `storage.py` интерфейс на 30 строк с локальным фолбэком по флагу — страховка, если MinIO заартачится на защите.

## 6. Веб-интерфейс — фактический состав страниц

**Авторизация** — один аккаунт из `.env` (по умолчанию `admin / admin`), без ролей.

**Главная** (`/`) — объекты карточками: название, тип, активные этапы, статус по открытым отклонениям (сегодня всегда «наблюдения нет» или «нет данных» — `deviations` пуста, §5), число кадров.

**Создание объекта** (`/sites/new`) — короче задуманного в первой версии плана: название, адрес, тип объекта, список этапов предвыбран по галочкам справочника (семь штук, §3.1), даты не заполняются здесь — их вносят на странице объекта. Шаг с загрузкой декларации и шаг с корпусами (этажность/площадь как веса свёртки) **убраны из формы** — декларация не парсится (§4.4), а базовый режим без корпусов (§3.2) стал единственным реализованным.

**Страница объекта** (`/sites/{id}`) — то, что было «дашбордом» в первой версии плана, плюс то, чего там не было:
- **диаграмма Ганта план/факт** (`_gantt.html`, §3.7): колонки недель/месяцев, фиксированные строки, две полосы плана и факта; соседние этапы перекрываются, линия «сегодня» и предупреждение о разрыве дат;
- прогресс объекта и каждого этапа — зелёные шкалы по видимым вехам, рядом полнота наблюдений; по этапам также предварительная вероятность срока и опережение/отставание в днях;
- кнопка «Указать» текущую дату для объекта (`sim_today`, §4.4) — эксперимент с историческим датасетом;
- календарный план: перетаскивание строк, даты дд/мм/гггг, поле «Загрузить план» — CSV/TXT, `app/plan_import.py`, §4.4;
- список камер объекта, добавление новой (поток/папка, включение маски чекбоксом при заведении).

**Страница камеры** (`/cameras/{id}`) — сильно отличается от первой версии плана:
- переименование камеры прямо здесь, без пересоздания;
- **маска не собирается автоматически — её один раз рисует оператор** кистью по первому кадру (`mask_editor.js`), с кнопкой «работать без маски» и переключением режима после заведения;
- состояние маски: доля скрытого, доля целого, число окон, верхняя граница — числа, не ползунок по времени (эволюция маски как проигрыватель, задуманная в первой версии плана, не сделана);
- для потоковой камеры — «Подключить»/«Отключить», статус ожидания кадров, параметры подключения (адрес, ключ) для запуска `simcam`;
- для камеры-папки — запуск и прогресс разбора истории;
- **индикатора «камера переставлена» и предложения перепривязать нет** — гомография не реализована, §3.4.6.

**Результаты прогона / принятые кадры** (`/cameras/{id}/frames`) — галерея кадров с тремя представлениями (с погашенным фоном / маска красным / исходник) и счётчиком «N «да» из 36» на карточке. Клик по кадру (`/frames/{id}`) — **ответы модели Б по чек-листу**, таблица «вопрос — ответ — ключ — этапы — задержка», фильтр «только да». Этого не было в первой версии плана вовсе.

**Настройки** (`/settings`) — тоже новое: профили модели Б (§4.2), переключение активного профиля, правка адреса/модели/ключа, кнопка «Проверить» живым вопросом по настоящему кадру.

**Чего из первой версии плана в интерфейсе нет:** ленты отклонений (нечего показывать — §3.11 не реализован), карточки прогноза (§3.8 не реализован), карточки по технике (§3.9 не реализован), зон корпусов и зоны отстоя (расширенный режим §3.2 не понадобился).

### 7.0. Демо-датасет — три камеры одной площадки

`data/raw_noon_images/` — три серии по одному кадру в день, около полудня, одна и та же стройка с трёх ракурсов (`corinthian`, `doric`, `ionic`):

| Камера | Кадров | Диапазон дат |
|---|---|---|
| corinthian | 580 | 12.10.2005 – 02.06.2008 |
| doric | 597 | 12.10.2005 – 03.06.2008 |
| ionic | 580 | 12.10.2005 – 02.06.2008 |

Съёмки почти синхронны (в пределах суток), поэтому годятся для проверки «да перевешивает нет» на реальных, не синтетических данных (§3.7 шаг 2). Ровно по этому датасету построен `data/plan_for_raw_noon_images.txt` — план из семи макроэтапов с конкретными датами, выведенными вручную по видимому на кадрах состоянию площадки (не из декларации — её у датасета нет). Каждая серия подаётся `simcam` на своём порту (§2, §6) с интервалом от 30 до 60 секунд вместо реальных 20 минут — для демо, не для оценки маски.

Первая версия плана предполагала интервал 20 минут и прореживание CCTV-датасета (19 982 кадра, медианный интервал 7 секунд) под этот темп — **прореживание не выполнялось**, `tools/thin_cctv.py` не существует. Основным для демо и разработки стал датасет `raw_noon_images` с уже естественным интервалом в сутки, а не CCTV.

### 7.1. Фотоотчёты наш.дом.рф — не реализовано

**Статус: роль не занята, парсер не строился.** Ниже — техническое задание из первой версии плана: застройщик обязан ежемесячно публиковать фотоотчёты с датой съёмки рядом с декларацией того же объекта, что дало бы ground truth для этапов, независимый источник этажности и материал для бэктестинга прогноза. `tools/parse_declaration.py` и `tools/nardom_photos.py` не существуют, `declarations` в БД не заполняется. Место наш.дом.рф в демо и разработке занял датасет `raw_noon_images` (§7.0) — он не даёт готовых деклараций и бэктестинга прогноза, но его метки времени сами по себе достаточно плотные для методики §3.7.

### 7.2. Метрики, которые предлагаем сами

Из первой версии плана. Отмечено, что реально посчитано:

1. **Точность определения макроэтапа** — accuracy и per-class F1 на размеченном срезе. 🔲 не размечено, не посчитано.
2. **Точность «работает / простаивает»**, отдельно — точность статуса `PARKED`. ❌ модель А заглушка, метрика неприменима.
3. **Точность измерения этажности** — MAE в этажах. 🔲 `mask_top_edge_px` копится (§3.6), в этажи не переводится.
4. **Качество маски** — IoU автоматической маски с размеченной вручную, время сходимости. ✅ частично: замеры F1 на двух прогонах Эдинбурга есть в докстринге `mask.py` и §3.4.3, на `raw_noon_images` отдельно не переизмерялось — маска там оператор-заданная, сходимости в прежнем смысле нет.
5. **Lead time предупреждения.** ❌ ранние индикаторы §3.8 уровень 5 не реализованы.
6. **MAE прогнозной даты** на горизонтах 30/50/70% истории. ❌ прогноза нет.
7. **Ложные тревоги на 100 камеро-дней.** ❌ аномалии §3.11 не реализованы.
8. **Время обработки кадра end-to-end.** ✅ считается неявно — задержка каждого ответа модели Б пишется в `checklist_answers.latency_ms`.

Единственная метрика с реальными числами на сегодня, не входившая в этот список: **доля дней, на которых признак этапа отвечает «да»** (`aggregate.constant_keys`, §3.7 шаг 4) — родилась не как метрика качества, а как защита от конкретного сбоя, но годится и для ревизии вопросов чек-листа перед демо.

## 8. Демо-сценарий

**Полностью переигран относительно первой версии плана.** Там демо строилось вокруг предрасчёта в БД и одного живого вызова модели Б «для честности». Реальность оказалась противоположной: живой потоковый приём камер — это и есть демо, не риск, который надо прятать за предрасчётом.

Сценарий по факту:
1. Поднять сервис и три процесса `simcam` (по одному на `corinthian`, `doric`, `ionic`, §7.0), каждый на своём порту, с интервалом 30–60 секунд вместо реальных 20 минут.
2. На странице каждой камеры нарисовать (или загрузить готовую) маску, нажать «Подключить» — камера начинает слать кадры на приёмник немедленно.
3. Каждый принятый кадр сразу проходит маску и модель Б — показать это на странице камеры (счётчик кадров растёт) и на странице кадра (ответы чек-листа появляются один за другим).
4. На странице объекта — диаграмма Ганта обновляется по мере съёмки: фактические полосы могут перекрываться у соседних этапов, а шкалы прогресса и оценки срока пересчитываются по подтверждённым вехам.
5. Показать переключение профиля модели Б в `/settings` без перезапуска сервиса — следующий кадр уже разбирается другим провайдером.
6. Живой инцидент как материал для демо, а не только для журнала: константный вопрос-признак (§3.7 шаг 4) можно показать на примере, как один неверно размеченный вопрос чек-листа держал систему на первом этапе тринадцать месяцев, и как структурная защита это чинит без правки CSV.

**Чего в демо нет и почему:** ленты отклонений и статусов техники — §3.9–3.11 пока не реализованы (§6). Прогноз срока присутствует на диаграмме как предварительная эвристика (§3.8). Ползунка «эволюция маски по времени» тоже нет — маска сегодня статична после одного клика оператора, эволюционировать во времени нечему показывать так эффектно, как в задумке первой версии плана.

**Открытый риск демо, а не методики:** живая инфраструктура (Postgres, MinIO, локальная модель, три процесса `simcam`) должна быть поднята заранее и остаться живой до защиты — при падении Docker-хоста (уже случалось на разработке, см. `AGENTS.md`) всё это нужно перезапускать руками, а состояние симулятора кадров (что уже отправлено) не персистентно между перезапусками процесса.

Риски первой версии плана, снятые переходом на оператор-заданную маску и живые данные (**больше не актуальны**): «маска не сходится», «в CCTV нет камеры с достаточно длинной историей», «нет размеченных этапов для оценки» — `raw_noon_images` дал готовую, плотную, почти синхронную по трём камерам историю с известными (пусть и вручную выведенными) датами этапов.

## 10. Открытые вопросы и нерешённые проблемы

### Закрыто

- [x] Башенный кран этапом не делаем — атрибут состояния площадки (в модели данных не заведён отдельно, но и `equipment_tracks` не используется вовсе, §3.9).
- [x] Паспорт продукта не используем.
- [x] Команда: соло. Стек и приоритеты пересобраны.
- [x] Хранение кадров: MinIO с локальным фолбэком.
- [x] **Уровень агрегации: объект, не корпус.** Корпуса — внутренняя единица измерения, свёртка по весам не реализована — работаем только в базовом режиме без корпусов, который сам §3.2 называет рекомендованным.
- [x] **Маска: оператор красит фон один раз, дальше только сжимается.** Решение изменилось относительно предыдущей версии (там — полностью автоматическая), но задача «ручная обводка контура не нужна» решена другим путём: один клик на камеру, не обводка контура на каждом кадре.
- [x] **Ночь: модель Б только днём.** (Модель А — заглушка, круглосуточность неприменима.)
- [x] **Даты: конкретные, не кварталы**, формат дд/мм/гггг.
- [x] **Семь макроэтапов, не восемь** — кровля и фасад слиты, §3.1.
- [x] **Камера как отдельный сервис**, приём кадров на лету, потоковый конвейер — этого не было в первой версии плана вовсе.
- [x] **Провайдер модели Б переключается в интерфейсе**, не только в `.env` — тоже новое.

### Отменено или заменено

- [x] ~~Этажность меряем по верхней границе маски~~ — измеряется, но не подключена к выводу об этапах (§3.6).
- [x] ~~Входы графика: все три~~ — реализовано два из трёх, декларация PDF не парсится (§4.4).

### Нерешённые проблемы — честный список

На защите лучше назвать самим, чем ждать вопроса из зала. Первые четыре — самые заметные, дальше по убыванию значимости.

1. **Предварительная вероятность срока не откалибрована.** Для демо она оценивается по темпу взвешенных вех одного объекта и показывается вместе с полнотой наблюдений. Для калибровки нужны размеченные истории нескольких объектов.

2. **Модель А — заглушка**, статусная машина техники и различение «присутствует/задействована» не встроены в поток. §3.9–3.11 не реализованы. Контракт зафиксирован — подмена возможна без переписывания остального.

3. **Перестановка камеры не обрабатывается.** Гомография из первой версии плана не закодирована; при физическом сдвиге камеры — ручной сброс маски и потеря истории. §3.4.6.

4. **Неоднозначный вопрос может дать ложный сигнал перехода.** Формулировки для участка, котлована, первого этажа, фасада и благоустройства уточнены; вопросы-константы и сигналы с открытыми зонами больше не служат единственным шлюзом этапа. Качество новых формулировок всё равно нужно оценить на полном архиве и вручную проверить кадры вокруг каждого перехода.

5. **Наблюдение не с нуля стройки — больше не проблема метода**, но остаётся проблемой процесса: оператор должен не забыть покрасить то, что уже построено, как объект, а не как фон, при заведении камеры на объекте, который уже строится.

6. **Фильтр смежности и ограничение прироста площади не реализованы.** Если демо-камера окажется рядом с посторонней динамикой (чужая стройка, проезжая часть вплотную), маска может начать неверно стирать соседние области. На датасете `raw_noon_images` риска нет, на реальной камере организатора — есть.

7. **Как гасить фон для VLM — не подтверждено окончательно.** DARKEN выбран по умолчанию, `tools/vlm_bench.py` меряет, но победитель не зафиксирован числом. §3.4.5.

8. **Слепые зоны.** Интерфейс показывает полноту наблюдений по весу доступных вех. На нескольких объектах ещё предстоит проверить, насколько этот индикатор совпадает с реальной видимостью работ.

9. **Экскаватор, работающий на месте**, читался бы как простой в §3.10 — неприменимо, пока модель А не реализована, но стоит помнить при реализации.

10. **Наш.дом.рф выпал из проекта целиком** — ни ground truth для этапов, ни бэктестинг прогноза, ни нормативы `stage_norms` из открытых данных не собраны. §7.1.

## 11. Порядок работ — что сделано, что осталось

Первая версия плана резала фичи по шагам вперёд. Реальность пошла не по шагам: конвейер, маска, семь этапов и предварительный прогноз готовы; статистическая калибровка прогноза ещё не выполнена. Ниже — состояние по факту, не план на будущее.

### Реализовано

- Оператор-заданная динамическая маска, монотонно сжимающаяся, с якорной нормировкой освещения (§3.4).
- Камера как отдельный сервис (`simcam/`), потоковый приём кадров на лету, очередь на камеру (§2, §6).
- Семь макроэтапов, уточнённые вопросы чек-листа с `latching`/`hint`, батч со схемой (§3.1, §3.5).
- Поэтапные начала с перекрытием соседних стадий и прогресс по взвешенным вехам (§3.7).
- Диаграмма Ганта план/факт, веса объёма работ, прогресс и предварительная оценка срока (§3.7, §3.8).
- Настройки: переключаемые профили модели Б, включая облачные (§4.2, §6).
- Просмотр ответов модели Б по каждому кадру (§6).

### Не начато

Список совпадает с журналом `AGENTS.md`, раздел «Не готово», и с §10 выше:

- Калибровка предварительной вероятности срока на нескольких размеченных объектах — §3.8.
- Интеграция модели А, статусная машина техники, аномалии — §3.9–3.11.
- Перепривязка маски при перестановке камеры — §3.4.6.
- Защищённые оператором зоны маски, фильтр смежности, ограничение прироста площади — §3.4.3.
- Парсер проектной декларации и фотоотчётов наш.дом.рф — §4.4, §7.1.
- Ползунок «эволюция маски по времени» для защиты — §6, §8.

### Режем без сожаления (осталось в силе)

- Редактирование шаблонов чек-листа из UI → правка `reference/*.csv` руками.
- Роли пользователей → один admin.
- Зоны корпусов, расширенный режим → базовый режим без корпусов, §3.2.
- Все измерения прогресса, кроме сбора ответов чек-листа, → по остаточному принципу.
