# AGENTS.md — протокол согласования между агентами команды

> Ветка: `dev-lamonifi` (Денис). `main` остаётся основной веткой репозитория —
> сюда никто не мержится без отдельного решения всей команды. Код в этой ветке
> принят как образец: остальные участники ориентируются на него, когда пишут
> свою обвязку и модели, но это не значит, что их ветки растут от неё в дереве
> git — у каждого своя ветка от `main`. `PLAN.md` остаётся документом для
> организаторов и содержит полную методику с обоснованиями; этот файл —
> рабочий слой поверх него, для координации между агентами разных участников
> в разных ветках.
>
> Если файл читает агент — см. «Протокол» ниже. Если человек — можно сразу
> перейти к «Текущее состояние».

---

## Зачем этот файл

Каждый участник работает в своей ветке со своим агентом. Ветки расходятся
быстрее, чем люди успевают друг друга услышать. Чтобы код, который генерирует
агент в одной ветке, не противоречил тому, что уже решено и сделано в другой,
каждая ветка ведёт свой `AGENTS.md` — журнал того, что сделано, почему именно
так и что было рассмотрено и отвергнуто. Отвергнутое важнее принятого: без
него следующий агент с шансами предложит то же самое и потратит цикл на
повторное открытие того, что уже проверено и не работает.

Это не отчёт для человека постфактум. Это вход, который агент обязан прочитать
**до**, а не после генерации кода.

## Протокол для агента

**Перед тем как начать работу в этой ветке:**

1. Прочитать раздел «Текущее состояние» и «Ключевые решения» целиком — это
   быстрее, чем заново вычитывать код и наступать на грабли, которые уже
   размечены.
2. Если задача касается общих файлов (модель данных, конвейер маски, роуты) —
   проверить, не ушли ли по этой же теме дальше в других ветках:

   ```bash
   git fetch github
   git branch -r                              # какие ветки вообще есть
   git log origin/<ветка-коллеги> -- AGENTS.md # история их журнала
   git show origin/<ветка-коллеги>:AGENTS.md   # текущее содержимое
   ```

   Дальше в ветках это будет `github/<ветка>`.

   Это можно не делать руками — в репозитории есть подагент
   `.claude/agents/team-sync.md`. Он читает `AGENTS.md` и код в чужих ветках,
   сверяет со контрактами из `PLAN.md` и «Ключевыми решениями» ниже, и
   докладывает расхождения в чат — ничего не пишет и не пушит сам. Вызывается
   вручную, когда попросишь агента свериться с командой перед началом работы
   над чем-то общим.
3. Если в чужом журнале есть решение, которое расходится с тем, что просит
   сделать пользователь в этой ветке — **не решать самому молча**. Сказать
   пользователю прямо: «в ветке X это решено иначе, вот расхождение» — и
   спросить, что важнее. Тихо выбрать одну из сторон значит закопать конфликт
   до мержа, где он всплывёт дороже.

**Во время работы, после каждого значимого шага** (не после каждой правки
файла, а после того как решена содержательная задача — добавлена функция,
принято архитектурное решение, отвергнут подход): дописать запись в «Журнал»
внизу этого файла. Значимый шаг — это то, что другой агент обязан знать перед
тем как трогать соседний код; опечатка в README под это не подпадает.

**Формат записи в журнале** — коротко, но так, чтобы решение было понятно без
чтения диффа:

```markdown
### 2026-09-24 · <кто/ветка> · <тема одной строкой>

Сделано: <что именно, файлы>.
Почему: <что заставило сделать именно так>.
Отвергнуто: <что рассматривали и почему не пошло, если applicable>.
Задевает: <какие файлы/модули общие — на что обратить внимание при мерже>.
```

**Что писать не нужно**: пересказ кода (он читаем сам), список запущенных
команд без результата, черновые варианты, от которых отказались в пределах
одной сессии, не дойдя до реализации.

## Текущее состояние

Стек: FastAPI + Jinja2 + HTMX + Tailwind CDN, без сборки фронтенда (см.
`README.md`, раздел «Структура»). Postgres — модель данных, MinIO/S3 —
кадры. Модель Б — внешний VLM по OpenAI-совместимому API.

Готово и проверено:

- **Динамическая маска фона** (`app/pipeline/mask.py`) — оператор один раз
  закрашивает фон на первом кадре, дальше маска только сжимается. Якорная
  нормировка освещения по самым спокойным клеткам. Замерено на двух реальных
  прогонах Эдинбурга (`tools/mask_bench.py`), F1 0.42–0.80 в зависимости от
  того, насколько застройка вообще отличима от фона на конкретной камере.
- **Веб-интерфейс камеры**: рисование маски кистью в браузере
  (`app/static/mask_editor.js`), выбор папки с кадрами проводником по ФС
  сервиса (`/api/fs`, `app/static/folder_picker.js`) — путь текстом не вводится.
  После подтверждения маски разбор истории запускается сам в фоновом потоке
  (`app/pipeline/runner.py`) с прогресс-баром на странице камеры.
- **Календарный план**: состав и порядок этапов редактируются на странице
  объекта — добавление из справочника, удаление, перетаскивание строк
  (`app/static/stages.js`). Порядок в БД совпадает с порядком строк в форме.
- **Дашборд** (`/`, `app/templates/dashboard.html`) — сводка по всем объектам:
  статусы графика, загрузка по этапам, отклонения, что требует внимания
  (камеры без маски или с исчерпанной маской).
- **Тёмная/светлая тема** — один файл `app/static/theme.css` поверх классов
  Tailwind, переключатель в шапке, выбор хранится в `localStorage`.
- Тесты: `tests/test_mask.py` (свойства маски — монотонность, устойчивость
  к погоде, реакция на рост здания), `tests/` для разбора ответа модели Б.
  `.venv/bin/python -m pytest tests/ -q`.

- **Чек-листы и разбор этапов**: содержимое в `reference/*.csv`, вопросы —
  общий пул с ключами, этап ссылается на ключ с полярностью. Модель Б
  вызывается батчем на чек-лист с жёсткой JSON-схемой. `aggregate.py`
  сворачивает хронологию ответов в отрезки активности этапов, карточка
  объекта показывает их против календарного плана. Включается флагом:
  `--model-b` у `tools/ingest_folder.py` или галочкой на странице камеры.

- **Камера как поток** (`simcam/`, `app/pipeline/live.py`) — камера живёт
  отдельным сервисом со своим адресом и шлёт кадры по одному; приложение
  разбирает каждый сразу по приходу. Приём защищён ключом на камеру
  (`Camera.ingest_key`), очередь на камеру одна и разбирается одним потоком —
  порядок кадров важен, маска зависит от предыдущих. `simcam` — имитатор:
  берёт кадры из папки и шлёт их с любой паузой, метки времени остаются
  настоящими.
- **Диаграмма Ганта** план/факт (`app/pipeline/gantt.py`, `_gantt.html`) —
  плановая полоса и по полосе на каждую камеру на общей шкале, мера
  совпадения по пересечению календарных дней. Обновляется сама, пока идёт
  съёмка. Тесты `tests/test_gantt.py`.

Не готово: вердикт (отставание / в срок / опережение) и прогноз задержки
(§3.7 п.7, §3.8) — отрезки активности и сравнение с планом в днях уже есть
(`gantt.Row.shift`, `.match`), прогноза пока нет. Модель А не подключена,
`model_a_url` пустой.

## Ключевые решения (что нельзя тихо переизобретать)

Подробное обоснование каждого — в `PLAN.md` (методика) и в шапках модулей
(`app/pipeline/mask.py` держит историю всех отвергнутых вариантов маски прямо
в докстринге — это не общие слова, а числа с конкретных прогонов).

- **Маска фона только сжимается, никогда не растёт.** Направление выбрано по
  цене ошибки: рост маски в пределе скрывает всё и рвёт разбор, сжатие в
  пределе — откат к полному кадру, не хуже, чем без маски вовсе. Автоматический
  вариант (маска растёт от пустой) **отвергнут**: на реальных данных фон
  (деревья, перепаханная земля) меняется не меньше, чем стройка, и авторост
  либо сходится к 6%, либо разъезжается до 100% в зависимости от параметра.
- **Сравнение по яркости, не по структуре.** HOG-градиенты и Hough-линии
  измерены и отвергнуты — F1 0.67 и 0.10 против 0.86 у яркости на текущих
  данных, потому что фон здесь не оконные сетки, а деревья и земля. Оговорка:
  в сценарии с соседними жилыми домами структурный признак может выиграть,
  но переключать эвристику без нового замера на новых данных нельзя.
- **MAD (медианное абсолютное отклонение) не годится для детекции изменения** —
  не видит ступенчатые изменения. Используется разность медиан половин окна.
- **Отложенное подтверждение стирания по обратимости, требование связности
  растущей области, отбрасывание одиночных клеток** — все три проверены
  замером на двух прогонах и **отвергнуты**: каждое покупает точность на
  одном прогоне ценой полноты на другом. Если кто-то предложит один из этих
  трёх подходов снова — сначала посмотреть числа в докстринге `mask.py`,
  не переизмерять с нуля.
- **Чек-лист вместо классификации этапа**, ответ тернарный (да/нет/не уверена).
  «Не уверена» — чтобы кадр без видимого признака не голосовал случайным «нет».
- **Темп считается по активным дням, не по календарным** — разделяет простой
  (темп нормальный, догонят) и перегрузку при полной занятости (темп низкий,
  разрыв будет расти).
- **Аналитика и вердикт — по объекту целиком, не по корпусам.** Прямое
  требование организаторов (см. PLAN.md §1.2). Корпус остаётся внутренней
  единицей измерения только для веса в свёртке.
- **Даты календарного плана — конкретные, не кварталы.** Тоже прямое
  требование организаторов, менять на диапазоны/кварталы нельзя.
- **VLM: qwen3-vl, порт 11435** (11434 занят на общей машине). Обсуждается
  переход с тега `qwen3-vl:30b` на официальный `qwen3-vl:30b-a3b-instruct` —
  первый, предположительно, всегда включает рассуждение перед ответом и ест
  бюджет токенов, второй — явный instruct-вариант без этого. Замерять через
  `tools/vlm_bench.py` перед тем как менять `VLM_MODEL` в `.env` у всех.
- **Отдельного фронтенда со сборкой нет.** Соло/командная разработка на
  сервере, HTMX для интерактивности. Не превращать в SPA без явного решения
  всей команды — это второй сервис и npm в докере ради страниц, которые и так
  рендерятся сервером.

## Соглашения по стилю

- Общение и комментарии в коде — по-русски.
- Комментарий объясняет **почему**, не **что** — если убрать его и ничего не
  станет непонятно, комментарий лишний.
- Без абстракций под гипотетическое будущее: три похожие строки лучше
  преждевременного обобщения.
- Не добавлять обработку ошибок для ситуаций, которые не могут произойти;
  валидация — только на границах системы (пользовательский ввод, внешние API).
- Тесты — pytest, `tests/`. Свойство, которое ловит регрессию (например
  «маска не растёт»), стоит больше, чем проверка happy path.

без потерь и повторов, маска двигается на смене суток, чек-листы копятся
раздельно по камерам, диаграмма перерисовывается сама.

Отвергнуто: обработка кадра прямо в HTTP-запросе камеры. Разбор занимает
секунды (с моделью Б — под десяток), камера в это время должна снимать.

Задевает: `Camera.ingest_key`, `Camera.last_seen_at`, `Frame.meta` — новые
колонки; `ingest.save_checklists` теперь возвращает число чек-листов;
`aggregate.site_curves` получил параметр `camera_id`, добавлен
`curves_by_camera`. Кто строит аналитику по объекту — учтите, что наблюдения
теперь разделимы по камерам.

Внимание тем, кто трогает исходящие HTTP-запросы: если в окружении есть
`HTTP_PROXY`, `requests` уведёт в него даже запрос на 127.0.0.1. Ключей в
`proxies` нужно три — `http`, `https` и `all`; без `all` обход не работает,
потому что requests сначала дописывает прокси из окружения, а уже потом
выбрасывает ключи со значением None.

### 2026-09-26 · api-solution · сервис на Streamlit + GLM API

Сделано: `api-solution/` — Streamlit-сервис: загрузка фото (дата из EXIF или
имени файла, правится вручную), разбор моделью `glm-4.6v` (z.ai), сводка с
прогресс-баром, этапом, отклонениями, план/факт и прогнозом. Модули в `core/`,

`tools/smoke.py` — проверка ключа на одном фото.

Почему так: решение пользователя — без локальных моделей, Streamlit без
стилей, бюджет $5 на API. Запрос на кадр в два шага (разведка → чек-лист 2–3
кандидатов), а не всё одним запросом — по замеру этой ветки длинный батч
схлопывает «не видно» в «нет». Стратегия подключаемая (`STRATEGIES`),
`per_stage` уже есть.

Отвергнуто:
- линейный прогноз по % готовности — ранние этапы лёгкие по весу и быстрые,
  прогноз выходил на месяцы раньше плана при фактическом отставании;
  заменён на темп относительно плана;
- доверять ответу на признак для любого этапа, где он встречается —
  общие признаки (траншея: 1.3 и 8.1) перебрасывали кадр на чужой этап;
  теперь ответам верим только по этапам-кандидатам разведки;
- «бетононасос без миксеров» на стоящем насосе — по PLAN §3.9 стоящая
  техника не повод для отклонения.

Задевает: `reference/checklist.json` — из 6.1 убран признак `formwork_floor`
(опалубка наверху — это каркас, не кровля). Стек отличается от
`dev-lamonifi` (FastAPI + HTMX) — это отдельное решение, при сведении веток
переиспользуемы `core/` (кроме `storage.py`) и `reference/`.

### 2026-09-26 · api-solution · тесты на test_photos, правка промптов по замеру

Сделано: `core/service.py` — сценарии без UI (приём, разбор, отчёт), app.py
только вызывает их. 54 офлайн-теста, в т.ч. весь сервис на 10 реальных фото с
«эталонной» моделью по разметке `tests/fixtures/ground_truth.json`. Live-тест
против разметки с записью ответов в кассету (`tests/cassette.py`): повторные
прогоны бесплатны. Потрачено на всё тестирование $0.056.

Результат `glm-4.6v` two_step: этап 9/10 (точно 8), $0.0018/фото.

Что замер показал и что поменяли:
- модель ни разу не отвечала «unsure» → вариант `not_visible` с правилом
  «прежде чем no — проверь, видно ли место»; доля «не видно» стала 0.4–0.7
  на фасадных кадрах, где низа площадки нет;
- на готовом фасаде «вероятность, что работы идут» по всем этапам ≈ 0 →
  этап терялся; добавлено поле разведки `latest_stage` (последний этап,
  работы ИЛИ результат которого видны) и приор 0.7 для него в scoring;
- разведка отстаёт на этап → в кандидаты всегда идёт latest_stage + 1;
- общие признаки (разработка грунта: 3.1 и 4.6) открывали следующий этап →
  фронт сдвигают только отличительные признаки этапа (`Checklist.distinctive`);
  у 4.6 свой признак `backfilling`; build.py предупреждает о подэтапах без
  отличительных признаков (сейчас только 8.1);
- балл этапа = доля must_have из чек-листа (если этап спрашивали), а не
  среднее с разведкой — разведка давала 0 армированию плиты;
- z.ai кэширует только текстовый префикс до картинки → текст теперь перед
  картинкой, статичные инструкции разведки идут по цене кэша;
- простои: только по соседним календарным дням и при доказательстве
  (обзорный кадр или явный 0 рабочих); «нет техники этапа» — только по
  обзорным кадрам; башенный кран не участвует в «вся техника стоит».

Отвергнуто по замеру: стратегия per_stage (7/10 против 9/10, дороже) —
отдельно спрошенный этап модель чаще подтверждает. glm-4.6v-flash — 429.

Задевает: `reference/checklist.json` (признак `backfilling`, подсказка `pit`).
Если в dev-lamonifi модель Б тоже спрашивает по признакам, общим для
нескольких этапов, там та же ловушка с «прыжком» этапа вперёд.
