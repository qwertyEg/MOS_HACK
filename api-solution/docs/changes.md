## v6.1 — «unable to open database file» при запуске (26.09.2026)

**Причина.** Streamlit держит объект `Storage` в кэше (`st.cache_resource`)
весь срок жизни процесса. Во время проверок перед v6 папка `data/`
удалялась (`rm -rf data`), пока приложение пользователя было запущено, —
объект продолжал ходить по пути к удалённому файлу, и sqlite падал на
каждой перерисовке.

**Исправлено.** `core/storage.py`: если файла базы нет, `Storage` пересоздаёт
папки и схему, а не падает; папка кадров создаётся при записи кадра.
Тест `test_storage_survives_deleted_data_dir`. Удалять `data/` проверки
больше не могут — с v6 интерфейс проверяется на временной базе.

**Последствие.** Если в удалённой `data/` были объекты и разборы
пользователя, они потеряны. Фото остались у пользователя в исходных файлах —
их можно загрузить заново; повторный разбор платный.

## v6 — проверка рисков после v5 (26.09.2026)

**Изменено**
- `reference/checklist.json`: башенный кран (`crane`) больше не обязательный
  признак этапа 5. Кран стоит с нулевого цикла (PLAN.md §3.1), поэтому он
  не признак каркаса. Сам вопрос остался в пуле: ключи совместимы с `dev-lamonifi`.
- `core/scoring.py`: одним отличительным признаком подэтапа этап открывается,
  только если разведка его допускает — это `latest_stage` или ниже, либо
  вероятность ≥ 0.3. Иначе нужен балл чек-листа ≥ 0.5.
- `core/analyzer.py`, `app.py`: переключатель «Учитывать историю стройки»
  (`use_context`), по умолчанию включён.
- `core/config.py`, `core/storage.py`: папка данных задаётся через
  `SERVICE_DATA_DIR`, путь к базе берётся при создании `Storage`, а не при
  импорте. Нужно, чтобы тесты не трогали рабочую `data/`.
- Тесты: `test_regressions.py` (8), `test_app.py` (3), 2 новых в
  `test_pipeline.py`, live-тест с ложной историей. Всего 83 без модели + 3 с моделью.

**Проверено** — таблица рисков в [testing.md](testing.md#проверка-рисков-после-v5).
Итог: ничего не сломалось. Контекст стройки на упорядоченной серии не
улучшает точность, стоит +24% и на неоднозначном кадре склонен держаться
за прошлый этап. Зато ложную историю модель не принимает и отмечает
противоречие явно.

## v5 — стройка целиком, план по фото, провайдеры (26.09.2026, промпты p3)

- Кадры объекта разбираются строго по дате. Каждый получает контекст по
  более ранним фото (`core/site.py: ContextBuilder`); поле разведки
  `context_conflict`, отклонение «снимок противоречит истории стройки».
- Этап, достигнутый по истории, всегда входит в кандидаты чек-листа.
- Сводка по стройке (вкладка «Стройка») и выгрузка CSV.
- Автоплан: от первой до последней даты фото, типовые пропорции этапов;
  источник плана `objects.plan_source` (auto / manual / file) с миграцией базы.
- Контракт модели и базовый клиент — `core/vlm.py`; z.ai — провайдер
  `core/glm.py`; реестр `core/providers.py`; слот локальной модели
  `core/local.py`, инструкция [local-model.md](local-model.md).
- Счётчик «ожидают разбора» учитывает кадры, у которых изменится история.

## v4 — отладка на реальных фото (26.09.2026, промпты p2)

- `core/service.py`: сценарии вынесены из `app.py`.
- Кассета ответов модели и live-тест против ручной разметки 10 фото.
- Промпты: ответ `not_visible`, поле `latest_stage`, уточнён признак котлована.
- Кандидаты: `latest_stage` и следующий за ним этап.
- Фронт работ сдвигают только отличительные признаки этапа; признак `backfilling`.
- Балл этапа — доля подтверждённых `must_have` из чек-листа, а не среднее с разведкой.
- Текст в запросе стоит перед картинкой, чтобы работал кэш z.ai.
- Простои считаются только по соседним дням и при доказательстве.
- Починка типовых поломок JSON до повторного запроса.
- Результат: этап 9/10, $0.0018 за фото.
