# Архитектура и как всё работает

## Общая схема

```
          фото (+ дата)
               │
     ┌─────────▼──────────┐
     │ приём (service)    │  дата: EXIF → имя файла → вручную
     │                    │  сжатие до 1280 px, sha256, сохранение,
     │                    │  пересчёт автоплана по датам фото
     └─────────┬──────────┘
               │  кадры объекта строго по дате съёмки
     ┌─────────▼──────────┐
     │ контекст стройки   │  что уже подтверждено по более ранним фото:
     │ (site)             │  этап, факты, техника
     └─────────┬──────────┘
               │
     ┌─────────▼──────────┐   есть в кэше? ──► берём готовый разбор, 0 токенов
     │ разбор (analyzer)  │
     │  шаг 1: разведка   │──► модель: ракурс, качество, техника, счётчики,
     │                    │        последний видимый этап, вероятности этапов,
     │                    │        противоречие с историей
     │  шаг 2: чек-лист   │──► модель: вопросы да / нет / не видно
     │                    │        только по 2–3 этапам-кандидатам
     └─────────┬──────────┘
               │           модель — любой провайдер из core/providers.py:
               │           z.ai (GLM) или локальная
               │
               │ JSON-ответы
     ┌─────────▼──────────┐
     │ оценка кадра       │  статусы подэтапов → фронт работ → % готовности
     │ (scoring)          │
     └─────────┬──────────┘
               │ все кадры объекта по датам
     ┌─────────▼──────────┐
     │ хронология         │  накопленный прогресс, простои, отклонения,
     │ (timeline, rules)  │  сравнение с планом, прогноз
     └─────────┬──────────┘
               │
     ┌─────────▼──────────┐
     │ сводка по стройке  │  техника за период, факты, этапы, противоречия,
     │ (site)             │  выгрузка CSV
     └─────────┬──────────┘
               │
          Streamlit (app.py)
```

## Модули

| Модуль | Что делает |
|---|---|
| `app.py` | Интерфейс: объекты, загрузка, сводка, кадры, план. Логики не содержит — вызывает `core/service.py` |
| `core/service.py` | Сценарии сервиса: принять фото, разобрать кадры по порядку дат с контекстом, автоплан, отчёт по объекту |
| `core/site.py` | База знаний по стройке: контекст для модели, сводка по всем фото, таблицы и CSV |
| `core/vlm.py` | Контракт модели (`ask_json → Reply`) и базовый OpenAI-совместимый клиент: ретраи, извлечение и починка JSON |
| `core/providers.py` | Реестр провайдеров моделей для интерфейса: z.ai и локальная |
| `core/local.py` | Слот локальной модели — реализация за Денисом, см. [local-model.md](local-model.md) |
| `core/images.py` | Дата съёмки (EXIF, имя файла), sha256, сжатие, data-URL для API |
| `core/glm.py` | Провайдер z.ai: ключ, параметр thinking, стоимость по тарифу |
| `core/prompts.py` | Тексты запросов к модели; собираются из `checklist.json` |
| `core/analyzer.py` | Разбор одного кадра: разведка → выбор кандидатов → чек-лист; кэш |
| `core/scoring.py` | Ответы по кадру → статусы подэтапов, фронт работ, % готовности |
| `core/timeline.py` | Серия кадров → накопленный прогресс, дни, простои, план/факт, прогноз |
| `core/rules.py` | Отклонения по одному кадру: техника не по этапу, парные правила |
| `core/plan.py` | Календарный план: типовые пропорции этапов, растяжение на период фото, загрузка CSV/XLSX |
| `core/storage.py` | SQLite: объекты, план, кадры, кэш разборов, журнал расходов |
| `core/checklist.py` | Доступ к справочнику этапов |
| `core/config.py` | Ключ, адрес API, модели и цены, размеры картинки, версия промптов |
| `reference/checklist.json` | Справочник этапов — источник правды для промптов и оценки |
| `reference/build.py` | Проверяет справочник, раскладывает строки xlsx, генерирует `checklist.md` |

## Справочник этапов

`reference/checklist.json` собран из xlsx организаторов (377 строк работ).
Подробно — в [reference/checklist.md](../reference/checklist.md).

- **8 макроэтапов** (как в ветке `dev-lamonifi`): подготовка → шпунт и сваи →
  котлован → подземный монолит → надземный монолит → кровля → фасад →
  наружные сети и благоустройство. Каждый имеет вес в общем проценте
  (надземный монолит 35%, фасад 18% и т.д.).
- **30 подэтапов**, к каждому привязаны строки xlsx. Работы, невидимые с
  камеры (внутренняя отделка, закупки, СКУД), помечены отдельно.
- **Признаки** — вопросы к модели («Виден ли открытый котлован…?») с подсказкой,
  как это выглядит. Этап ссылается на признаки: `must_have` — результат этапа
  виден, `must_not_have` — противоречит этапу. Подэтап: `active_when` — работы
  идут, `done_when` — результат есть.
- **latching** — признак, который после подтверждения не пропадает
  (котлован вырыт — значит был вырыт).
- **Техника этапа**: ожидается / возможна / не по этапу.

После правки JSON: `cd reference && ../.venv/bin/python build.py` — проверит
ссылки и пересоберёт `checklist.md`.

## Провайдеры моделей

Вся логика выше клиента модели знает о нём только одно: метод
`ask_json(system, image_url, prompt, max_tokens) → Reply` и атрибуты
`provider`, `model`, `thinking` (`core/vlm.py`). Провайдеры:

| Провайдер | Класс | Статус |
|---|---|---|
| `zai` — облако | `core/glm.py: GLMClient` | работает, по умолчанию `glm-4.6v` |
| `local` — локальная модель | `core/local.py: LocalVLMClient` | слот; реализация и замер — Денис ([local-model.md](local-model.md)) |

Оба наследуют `OpenAICompatibleClient`: z.ai, Ollama, vLLM и LM Studio говорят
на одном протоколе, отличаются только полями запроса и стоимостью. Выбор —
в боковой панели. Кэш разборов у провайдеров раздельный.

## Запросы к модели

По умолчанию — `glm-4.6v` через z.ai, рассуждение (thinking) выключено.
На каждое фото — два запроса:

**Шаг 1. Разведка.** В запросе — справочник техники, краткие описания 8
этапов и схема ответа. Модель возвращает: качество кадра, ракурс (сверху /
сбоку / с земли), описание, технику по типам (сколько всего и сколько
работает), число рабочих, этажей, остеклённых этажей, % облицовки,
% котлована, `latest_stage` (самый поздний этап, работы или результат
которого видны) и вероятность для каждого этапа.

**Выбор кандидатов.** `latest_stage`, следующий за ним этап, этап,
достигнутый по истории стройки, и этапы с вероятностью ≥ 0.3 — всего не
больше трёх.

**Шаг 2. Чек-лист.** Вопросы только по признакам этапов-кандидатов, ответ
`yes / no / not_visible` на каждый.

Как это настраивается:
- **Стратегия** (`core/analyzer.py: STRATEGIES`) решает только, как
  кандидаты раскладываются по запросам: `two_step` — все одним запросом
  (по умолчанию), `per_stage` — по запросу на этап. Переключается в UI.
- **Порядок в запросе**: системный промпт → неизменная инструкция →
  контекст стройки → картинка. z.ai кэширует только текст до картинки и
  только до первого отличия, поэтому инструкция стоит первой (её цена со
  второго фото в 6 раз ниже), а контекст, свой у каждого кадра, — после.
- **JSON**: у vision-моделей GLM нет режима принудительного JSON. Ответ
  вырезается из текста, типовые поломки (заглушки `<int>`, висячие запятые)
  чинятся, при неудаче — один повторный запрос с напоминанием о формате.
- **Кэш разборов** в SQLite по ключу (sha256 фото, провайдер, модель,
  thinking, стратегия, хэш checklist.json, версия промптов, хэш контекста
  стройки). То же фото с той же историей повторно не оплачивается. После правки промптов в `core/prompts.py` нужно поднять
  `PROMPT_VERSION` в `config.py`, правка `checklist.json` сбрасывает кэш сама.

## Как определяется этап и прогресс кадра (`scoring.py`)

1. **Статус подэтапа**: «идёт», если хоть один признак `active_when` = да;
   «готов», если все `done_when` = да; иначе «не начат» или «нет данных».
2. **Ответам чек-листа верим только по этапам-кандидатам.** Признаки бывают
   общими для нескольких этапов, и без этого ответ, данный для одного этапа,
   засчитывался бы другому.
3. **Балл этапа** — доля подтверждённых `must_have` минус штраф за
   `must_not_have`. Если этап чек-листом не проверяли — вероятность из
   разведки. Для `latest_stage` вероятность не ниже 0.7.
4. **Фронт работ** — самый поздний этап, который «виден»: балл ≥ 0.5 или
   сработал отличительный признак подэтапа. Отличительный — такого нет
   среди положительных признаков более ранних этапов. Без этого «идёт
   разработка грунта» (котлован) открывала этап «засыпка пазух». Одним
   признаком этап открывается, только если разведка его допускает
   (`latest_stage` или ниже, либо вероятность ≥ 0.3).
5. **Прогресс**: этапы до фронта выполнены (кроме подэтапов, которые на кадре
   явно ещё идут); подэтапы фронта: готов = 1, идёт = 0.5 или числовая
   метрика (этажи из N, % облицовки), не начат = 0; этапы после фронта = 0.
   Общий % = Σ вес этапа × прогресс этапа.

## Контекст стройки и база знаний (`site.py`)

Кадры одного объекта разбираются строго по дате съёмки. Перед каждым кадром
`ContextBuilder` собирает по уже разобранным более ранним фото короткую
сводку и передаёт её модели в обоих запросах:

```
Контекст этой стройки по 5 предыдущим снимкам (последний — 05.10.2006):
- достигнутый этап: 5 «Монолит надземной части» (с 05.10.2006); этапы 1–4 выполнены.
- уже подтверждено: шпунтовое ограждение (08.03.2006); открытый котлован (08.03.2006); …
- техника, которую уже видели на площадке: Башенный кран (до 2), Экскаватор (до 1), …
Стройка не идёт назад. … Если снимок явно противоречит контексту, коротко опиши это в поле context_conflict.
```

Что это даёт: разборы не противоречат друг другу; этап, достигнутый по
истории, всегда входит в кандидаты; противоречие модель отмечает явно, и оно
попадает в отклонения («снимок противоречит истории стройки»).

Переключатель «Учитывать историю стройки» в боковой панели (по умолчанию
включён) позволяет разбирать кадры по одному — результаты замера обоих
режимов в [testing.md](testing.md#проверка-рисков-после-v5).

Цена: хэш контекста входит в ключ кэша. Фото, загруженное задним числом,
меняет историю всех более поздних кадров — они становятся «ожидающими
разбора» и переразбираются (вкладка «Загрузка» показывает их число).
Контекст у каждого кадра свой и в кэш z.ai не попадает: около +500 входных
токенов на фото. Замер: $0.0020 против $0.0016 за фото без контекста.

**Сводка по стройке** (вкладка «Стройка») собирается из сохранённых
разборов всех фото, отдельно не хранится — поэтому всегда согласована с
фото:
- техника за весь период: на скольких фото и днях, максимум одновременно,
  доля в работе, первое и последнее появление, на каких этапах;
- подтверждённые факты с датой и фото, где впервые подтверждены;
- этапы: готовность, когда начат и завершён, плановые даты;
- противоречия с историей.

**Выгрузка CSV** (`;`, UTF-8 с BOM — открывается в Excel): по каждому фото
(этап, готовность, техника по типам — всего и в работе, рабочие, этажи,
отклонения, стоимость), техника, этапы, отклонения.

## Календарный план (`plan.py`, `service.refresh_auto_plan`)

- **Автоплан** (по умолчанию для нового объекта): период от первой до
  последней даты фото, внутри — типовые пропорции 8 этапов с перекрытиями
  (каркас самый длинный, фасад идёт параллельно с ним). Пересчитывается при
  каждом добавлении и удалении фото. Нужны фото минимум за два разных дня.
- **Вручную** (редактирование таблицы) или **файлом** (CSV/XLSX: этап,
  начало, окончание) — после этого план не меняется при загрузке фото;
  кнопка «Вернуть автоплан» возвращает автоматический режим.

## Серия кадров (`timeline.py`)

- Кадры сортируются по дате съёмки.
- Признаки `latching` после первого «да» держатся и дальше; прогресс этапа —
  накопленный максимум. Неудачный ракурс не откатывает объект назад.
- **По дням**: техника (максимум по кадрам дня), рабочие, активен ли день.
  **Простой** — день без работающей техники и рабочих, но только если это
  доказано: есть обзорный кадр или модель явно насчитала 0 рабочих (на виде
  фасада сбоку площадки просто не видно). Серия простоя — только по соседним
  календарным дням.
- **План/факт**: плановая готовность на дату — линейно внутри каждого этапа.
  Отставание в днях = на сколько раньше по плану должна была быть достигнута
  фактическая готовность. ±7 дней — «в срок».
- **Прогноз окончания** — по темпу относительно плана: во сколько раз
  фактический прирост готовности быстрее или медленнее планового за тот же
  период. Без плана — линейно.

## Отклонения (`rules.py` + `timeline.py`)

По кадру:
- работает техника из списка «не по этапу» для текущего этапа;
- экскаватор работает без самосвалов (пример из ТЗ) — снижение темпа;
- самосвалы стоят без погрузки;
- работающий бетононасос без бетоносмесителей;
- асфальтоукладчик без катка; буровая без миксера на этапе свай;
- на площадке ≥ 2 единиц техники и ни одна не работает (башенный кран не в счёт).

По дням и плану:
- за день не замечено ни одной единицы ожидаемой техники этапа (только по обзорным кадрам);
- простой 3+ дня подряд;
- этап должен был завершиться, но не завершён (critical после 14 дней);
- этап должен был начаться, но признаков нет; этап начат раньше плана;
- снимок противоречит истории стройки (модель заполнила `context_conflict`).

Одинаковые отклонения в соседние дни склеиваются в одно с диапазоном дат.

## Данные (SQLite, `data/service.sqlite`)

| Таблица | Что хранит |
|---|---|
| `objects` | объект: название, тип, этажность, источник плана (auto / manual / file) |
| `plan` | даты начала и окончания 8 этапов объекта |
| `frames` | кадр: объект, sha256, имя файла, дата съёмки, откуда дата, путь к сжатому JPEG |
| `analyses` | кэш разборов: ключ, модель, стратегия, полный JSON результата |
| `calls` | журнал вызовов API: шаг, токены (в т.ч. из кэша), стоимость, задержка |

Сжатые кадры — `data/images/<sha256>.jpg`.

## Настройки

`.env`: `ZAI_API_KEY`, `ZAI_BASE_URL`, `GLM_MODEL`; для локальной модели —
`LOCAL_VLM_BASE_URL`, `LOCAL_VLM_MODEL`, `LOCAL_VLM_API_KEY`;
`SERVICE_DATA_DIR` — другая папка для базы и кадров (по умолчанию `data/`). Остальное — в
`core/config.py`: цены моделей, размер картинки (1280 px), версия промптов.
Пороги логики — константы в начале `analyzer.py`, `scoring.py`, `timeline.py`.
