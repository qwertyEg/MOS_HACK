# Тесты

## Как запускать

```bash
cd api-solution
.venv/bin/python -m pytest                      # 83 теста без модели: бесплатно, ~5 с
.venv/bin/python -m pytest -m live -s           # 3 теста с моделью GLM (см. ниже про кассету)
.venv/bin/python tools/smoke.py <фото>          # один кадр через модель, вывод в консоль
```

Варианты live-прогона:

```bash
GLM_EVAL_MODEL=glm-4.6v-flash  .venv/bin/python -m pytest -m live -s   # другая модель
GLM_EVAL_STRATEGY=per_stage    .venv/bin/python -m pytest -m live -s   # другая стратегия запросов
GLM_EVAL_THINKING=1            .venv/bin/python -m pytest -m live -s   # с рассуждением
GLM_EVAL_PROVIDER=local        .venv/bin/python -m pytest -m live -s   # локальная модель (docs/local-model.md)
GLM_EVAL_CONTEXT=0             .venv/bin/python -m pytest -m live -s   # без истории стройки (A/B)
```

Порядок работы такой: сначала отлаживается всё, что не требует модели
(обычный `pytest`), и только потом — модель (`-m live`).

## Что такое «кассета» и зачем она

Каждый запрос к GLM стоит денег. При отладке одни и те же 10 фото
прогоняются много раз, а меняется обычно одна мелочь — формула оценки
этапа, правило отклонения, подсказка к одному вопросу.

**Кассета** (`tests/fixtures/glm_cassette.json`) — это файл, в который
записывается каждый ответ модели. Ключ записи — хэш того, что ушло в модель:
модель + промпт + картинка. Работает как магнитофон:

- запрос, который уже был, **воспроизводится из файла** — без сети, без
  ключа, бесплатно и мгновенно;
- новый запрос (изменился промпт или фото) **записывается** — уходит в
  API, ответ дописывается в файл.

Что это даёт:

- правка логики оценки, правил, хронологии проверяется на настоящих
  ответах модели за $0 (так проверялся переход на новую формулу балла
  этапа — 20 запросов из кассеты, 0 новых);
- после правки одного промпта оплачиваются только изменившиеся запросы
  (правка чек-листа этапа 4 — перезаписано 4 запроса из 20);
- live-тесты проходят у любого участника команды без ключа, если кассета
  лежит в репозитории;
- сырой текст ответа хранится как есть и при воспроизведении снова проходит
  через парсер JSON — парсер тоже тестируется на реальных ответах.

Реализация — `tests/cassette.py`, это обёртка над `GLMClient` с тем же
методом `ask_json`. В самом сервисе её нет: у сервиса свой кэш разборов в
SQLite (повторное фото не оплачивается), а кассета — только для тестов.

| `test_pipeline.py` (23) | Выбор кандидатов, нормализация ответов; стратегии меняют только число запросов; кэш не тратит токены; оценка кадра (каркас 8 из 16 этажей, не стройка); хронология не откатывается, latching держится; отклонения (пример из ТЗ, техника не по этапу, простой); вердикт и прогноз по плану, допуск ±7 дней; согласованность справочника; **регрессии с прогона на фото** (см. ниже) |
| `test_service.py` (13) | **Весь сервис на 10 реальных фото** с «эталонной» моделью, отвечающей по разметке: даты из имён, сжатие без увеличения, повторная загрузка, фото без даты отклоняется, полный отчёт (этапы по кадрам = разметке, прогресс монотонный, прогноз, план), второй прогон бесплатен, сбой одного кадра не останавливает остальные, смена модели не прячет старые результаты; **автоплан** от первой до последней даты фото и его пересчёт при удалении, ручной план не перезаписывается; **контекст**: кадры идут строго по датам и каждый видит историю, фото задним числом отправляет более поздние кадры на переразбор, противоречие с историей становится отклонением |
| `test_site.py` (5) | Контекст накапливает этап, факты с датами и технику; попадает в оба запроса и в ключ кэша; этап из истории всегда в кандидатах; сводка по стройке (техника за период, первое появление, этапы); CSV открывается в Excel и содержит колонки по каждому типу техники |
| `test_regressions.py` (8) | Риски после v5 — см. раздел ниже: z.ai не обходит системный прокси, миграция старой базы, удаление всех фото, план на двух соседних днях, разборы старого формата, 300 кадров, выключение контекста, ложная история не переписывает сам кадр |

| `test_providers.py` (6) | **Контракт провайдера**: каждый провайдер из реестра (z.ai и локальный) проходит весь путь разведка → чек-лист → этап на подменённой сети; кэш у провайдеров раздельный; локальный обходит прокси и не шлёт `thinking`; неподключённый локальный падает до сети с понятной ошибкой |

| Тест | Что делает |
|---|---|

## Проверка рисков после v5

После v5 (провайдеры, контекст стройки, автоплан) проверено, что ничего не
сломалось и не стало хуже. Для каждого сценария — тест.

| # | Риск | Проверка | Результат |
|---|---|---|---|
| 1 | Проверки интерфейса стирают рабочую базу `data/` | `test_app.py` на временной базе, `SERVICE_DATA_DIR` | Раньше скрипты проверки удаляли `data/` — **исправлено**, тест следит, что рабочая папка не меняется |
| 2 | Рефакторинг клиента изменил запросы к z.ai | 8 тестов клиента + `test_zai_keeps_system_proxy` | Не изменил: тело запроса, ретраи, стоимость те же; обход прокси только у локальной модели |
| 3 | База старого формата не откроется | `test_old_database_migrates_without_losing_data` | Колонка добавляется, объекты и план сохраняются; старые объекты получают автоплан |
| 4 | Крайние случаи плана | удалены все фото; фото на двух соседних днях | План очищается или строится корректно, отчёт не падает |
| 5 | Разборы старого формата без новых полей | `test_analysis_from_previous_version_still_renders` | Показываются (помечены устаревшими), идут в сводку, CSV и контекст |
| 6 | Страница стала медленнее (каждый показ — проход по всем кадрам) | 300 кадров: приём + разбор + отчёт + счётчик | 1.5 с на весь тест, отчёт с перерисовкой — доли секунды |
| 7 | Интерфейс | `test_app.py`: вкладки, неподключённая локальная модель, переключатель контекста | Работает; при выборе локальной модели результаты z.ai остаются видны |
| 8 | Контекст ухудшил качество | A/B на модели: с контекстом и без | См. ниже: найдены и исправлены две слабости методики, остался эффект якорения |
| 9 | Каскад ошибки: ложная история тянет этап | live: ранним фото — история «готовый фасад» | Этап не сдвинулся (3 и 4, как без истории); противоречие отмечено на обоих кадрах |

**Что показал A/B (риск 8).** Первый прогон с контекстом дал «точно» 7/10
против 8/10 без него. Разбор ответов показал, что виноват не контекст:
- на армировании плиты этап 5 (каркас) стал кандидатом из истории, и его
  чек-лист засчитал «башенный кран» и «опалубку наверху» (модель приняла
  опалубку стен подвала). Кран стоит с нулевого цикла и не может быть
  признаком каркаса → убран из обязательных;
- одним отличительным признаком этап открывался даже при нулевой оценке
  разведки → теперь нужен допуск разведки или половина обязательных признаков.

После исправлений кадр определяется верно. Но на другом, неоднозначном
кадре 320×256 на стыке этапов 4 и 5 модель с историей «достигнут этап 4»
ставит 4, без истории — 5. Это якорение: переход между этапами с контекстом
фиксируется на кадр позже. На этой серии (фото по порядку, одна стройка)
контекст не дал выигрыша в точности и стоит +24%. Его польза — в
согласованности и в том, что ложную историю модель не принимает и явно
отмечает (риск 9). Контекст оставлен включённым по умолчанию (требование:
разборы не должны противоречить друг другу); переключатель в боковой
панели позволяет разбирать кадры по одному.

Проверка на модели для рисков 8–9 стоила $0.025.

### Отчёт по объекту на реальных ответах

Прогресс 90%, текущий этап 7 (фасад). Отклонения: «экскаватор работает без
самосвалов» (3 кадра, самосвалов в кадре действительно нет), «техника не
работает» (1), «благоустройство не завершено в срок». Вердикт по графику —
«отставание», но план здесь придуманный (типовой от 01.10.2005), так что
вердикт показывает только, что механизм работает.
