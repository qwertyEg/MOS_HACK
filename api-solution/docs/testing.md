# Тесты

## Как запускать

```bash
cd api-solution
.venv/bin/python -m pytest                      # 54 теста без модели: бесплатно, ~2 с
.venv/bin/python -m pytest -m live -s           # 2 теста с моделью GLM (см. ниже про кассету)
.venv/bin/python tools/smoke.py <фото>          # один кадр через модель, вывод в консоль
```

Варианты live-прогона:

```bash
GLM_EVAL_MODEL=glm-4.6v-flash  .venv/bin/python -m pytest -m live -s   # другая модель
GLM_EVAL_STRATEGY=per_stage    .venv/bin/python -m pytest -m live -s   # другая стратегия запросов
GLM_EVAL_THINKING=1            .venv/bin/python -m pytest -m live -s   # с рассуждением
```

Порядок работы такой: сначала отлаживается всё, что не требует модели
(обычный `pytest`), и только потом — модель (`-m live`).

## Что такое «кассета» и зачем она

Каждый запрос к GLM стоит денег. При отладке одни и те же 10 фото
прогоняются много раз, а меняется обычно одна мелочь — формула оценки
этапа, правило отклонения, подсказка к одному вопросу.

**Кассета** (`tests/fixtures/glm_cassette.json`) — это файл, в который
записывается каждый ответ модели. Ключ записи — хэш того, что ушло в модель:
модель + промпт + картинка. Работает как магнитофон:

- запрос, который уже был, **воспроизводится из файла** — без сети, без
  ключа, бесплатно и мгновенно;
- новый запрос (изменился промпт или фото) **записывается** — уходит в
  API, ответ дописывается в файл.

Что это даёт:

- правка логики оценки, правил, хронологии проверяется на настоящих
  ответах модели за $0 (так проверялся переход на новую формулу балла
  этапа — 20 запросов из кассеты, 0 новых);
- после правки одного промпта оплачиваются только изменившиеся запросы
  (правка чек-листа этапа 4 — перезаписано 4 запроса из 20);
- live-тесты проходят у любого участника команды без ключа, если кассета
  лежит в репозитории;
- сырой текст ответа хранится как есть и при воспроизведении снова проходит
  через парсер JSON — парсер тоже тестируется на реальных ответах.

Реализация — `tests/cassette.py`, это обёртка над `GLMClient` с тем же
методом `ask_json`. В самом сервисе её нет: у сервиса свой кэш разборов в
SQLite (повторное фото не оплачивается), а кассета — только для тестов.

## Состав тестов

### Без модели — 54 теста (`pytest`)

| Файл | Что проверяет |
|---|---|
| `test_io.py` (17) | Извлечение JSON из ответа (```-ограждения, `<think>`, мусор вокруг), починка заглушек и висячих запятых; даты из имён файлов разных форматов; EXIF-дата важнее имени; сжатие до 1280; разбор плана из CSV |
| `test_glm_client.py` (8) | HTTP-клиент на подменённой сети: форма запроса (модель, thinking, текст перед картинкой), стоимость с учётом кэшированных токенов, ретраи на 429/5xx, 401 без повтора, повтор при битом JSON и оплата обоих вызовов, отказ после второго битого ответа, ошибка без ключа до сети |
| `test_pipeline.py` (21) | Выбор кандидатов, нормализация ответов; стратегии меняют только число запросов; кэш не тратит токены; оценка кадра (каркас 8 из 16 этажей, не стройка); хронология не откатывается, latching держится; отклонения (пример из ТЗ, техника не по этапу, простой); вердикт и прогноз по плану, допуск ±7 дней; согласованность справочника; **регрессии с прогона на фото** (см. ниже) |
| `test_service.py` (8) | **Весь сервис на 10 реальных фото** с «эталонной» моделью, отвечающей по разметке: даты из имён, сжатие без увеличения, повторная загрузка, фото без даты отклоняется, полный отчёт (этапы по кадрам = разметке, прогресс монотонный, прогноз, план), второй прогон бесплатен, сбой одного кадра не останавливает остальные, смена модели не прячет старые результаты |

Кроме того, интерфейс проверялся через Streamlit `AppTest`: все 4 вкладки
рендерятся на тестовых данных без исключений.

### С моделью — 2 теста (`pytest -m live`)

| Тест | Что делает |
|---|---|
| `test_connectivity_on_free_model` | Ключ, адрес и формат ответа — один запрос к бесплатной `glm-4.6v-flash` на маленьком кадре |
| `test_model_against_ground_truth` | 10 фото через весь сервис, сравнение с разметкой. Порог: этап в допуске ≥ 7/10, лишняя техника ≤ 2 кадров, < $0.01 за фото. Пишет отчёт `tests/fixtures/live_report_<модель>_<стратегия>.json` и печатает таблицу |

## Результаты

### Модель против разметки (`glm-4.6v`)

| Прогон | Этап в допуске | Точно | Ракурс | Лишняя техника | $ / фото |
|---|---|---|---|---|---|
| 1. two_step, исходные промпты | 8/10 | 7 | 9/10 | 0 | 0.0021 |
| 2. two_step, промпты p2 | 9/10 | 8 | 9/10 | 0 | 0.00185 |
| 3. + свой признак засыпки, отличительные признаки | 8/10 | 7 | 9/10 | 0 | 0.0018 |
| **4. + балл этапа = чек-лист (текущая версия)** | **9/10** | **8** | 9/10 | 0 | **0.0018** |
| per_stage (для сравнения) | 7/10 | 6 | 9/10 | 0 | 0.0023 |
| glm-4.6v-flash (бесплатная) | — | — | — | — | 0 |

- Прогон 3 исправил одну ошибку (котлован превращался в подземный монолит), но
  открыл другую (армирование плиты уходило в котлован); прогон 4 закрыл её.
  Что именно менялось — в [history.md](history.md).
- `per_stage` хуже: спрошенный отдельно этап модель чаще подтверждает
  (кровельные признаки на кадрах каркаса → этап 6 вместо 5).
- `glm-4.6v-flash` не прошла: 429 «сервис перегружен» и один ответ, не
  разобравшийся как JSON.

Остающаяся ошибка — фото 2005-12-23: разметка — сваи (этап 2), модель
уверенно видит открытый котлован с отвалами (этап 3). Кадр спорный,
подгонять промпт под одно фото на выборке из 10 не стали.

Доля ответов «не видно» после правки промптов: 0 на обзорных кадрах
котлована, 0.4–0.7 на фасадных (там низа площадки нет — это правильно).
До правки — 0 везде.

Прогресс 90%, текущий этап 7 (фасад). Отклонения: «экскаватор работает без

работает» (1), «благоустройство не завершено в срок». Вердикт по графику —

вердикт показывает только, что механизм работает.
