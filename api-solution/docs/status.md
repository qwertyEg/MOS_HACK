# Статус

## Сделано

- **Справочник этапов** (`reference/`): 8 этапов, 30 подэтапов, 60 признаков,
  21 тип техники, метрики, правила отклонений, веса; все 377 строк xlsx
  разложены и проверены скриптом.
- **Сервис** (`core/`, `app.py`):
  - приём фото, дата из EXIF или имени файла, ручная правка;
  - разбор моделью `glm-4.6v` в два шага, подключаемая стратегия запросов;
  - кэш разборов и журнал расходов в SQLite;
  - этап, подэтапы, % готовности, прогресс-бары по этапам;
  - техника с признаком «работает / стоит», рабочие, этажи, облицовка;
  - отклонения «этап → техника», простои, план/факт в днях, прогноз;
  - календарный план: автоматически по датам фото, ручной ввод, загрузка CSV/XLSX;
  - разборы по порядку дат с контекстом стройки, отметка противоречий;
  - сводка по всей стройке (техника, факты, этапы) и выгрузка CSV;
  - выбор модели: z.ai или локальная (слот, контракт, инструкция).
- **Тесты**: 83 без модели (весь сервис, включая 10 реальных фото, контракт
  провайдеров, интерфейс, риски после v5), 3 с моделью через кассету.
  Модель на 10 фото: этап 9/10, $0.0020 за фото. Журнал версий — [changes.md](changes.md).
- **Документация**: `README.md`, `docs/`.

## Осталось

### В работе у команды

- **Локальная модель** — Денис: довести `core/local.py`, прогнать контрактный
  и live-тест, сравнить с GLM ([local-model.md](local-model.md)).

### Важно для защиты

- **Больше фото для проверки.** 10 фото одной стройки — мало. Нужно 20–30 с
  других объектов, особенно этапы 1, 6 (кровля) и 8 (благоустройство) — в
  текущей выборке их нет. Прогон 30 фото ≈ $0.07.
- **Реальный календарный план.** Автоплан по датам фото показывает перекосы
  между этапами, но не отставание от договорного графика — для вердикта
  нужен реальный план объекта (загрузка файлом уже есть).
- **«Работает / стоит» по соседним кадрам.** Сейчас — по одному кадру (поза
  техники, люди рядом), на одиночном кадре это ненадёжно. Нужно поле
  «камера» у кадра и сравнение положения техники между соседними кадрами
  одной камеры (метод, подсказанный организаторами, PLAN.md §3.10).
- **Зоны площадки.** ТЗ: «техника не в своей зоне — аномалия». Не сделано.

### Решить команде

- **Контекст стройки по умолчанию.** Включён (разборы согласованы, ложная
  история отмечается), но на упорядоченной серии точность «точно» 7/10 против
  8/10 без него и +24% к цене. Проверить на второй стройке и решить.

### Можно улучшить

- Метрики этапов из `checklist.json`, которым нужен поток кадров (рейсы
  самосвалов, машино-часы), пока не считаются — нужна частая съёмка одной камеры.
- Сравнить thinking на трудных кадрах (дороже в несколько раз).
- Ночные и плохие кадры: модель помечает качество, но отдельной логики нет.
- Спорное фото 2005-12-23 (сваи или котлован) — пересмотреть после
  расширения выборки, не подгоняя промпт под один кадр.
- Кнопка «удалить объект» и редактирование названия в UI.

### Ограничения, о которых стоит помнить

- Готовность — только по работам, видимым снаружи.
- Простой считается только по дням, за которые есть фото.
- Этажи и % облицовки — оценка модели, не измерение.
- `glm-4.6v-flash` (бесплатная) для работы не годится — перегружена.
