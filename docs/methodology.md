# Методика СтройВзора: план, нормы «этап → техника», отклонения, план/факт

> Документ модуля «План + аналитика» (`core/plan/**`, `core/analytics/**`). Разделы о детекции техники
> (модель А) и определении этапа по снимкам (модель Б) дописывают их модули.
> Всё, что здесь описано, проверяется тестами `tests/core/test_plan_*.py` и `tests/core/test_analytics_*.py`.

Коротко: снимки → **модель А** (техника, «работает/стоит», моточасы) и **модель Б** (этап по чек-листу) →
**сопоставление с календарным планом** по явным правилам «этап → техника» → **отклонения с объяснением
и снимками-доказательствами** → вердикт по объекту «отставание / соответствие / опережение» с прогнозом.

## 1. Каталог работ организаторов

### 1.1. Канон — `reference/work_map.csv`

«Сводный перечень строительных работ» (`reference/works_catalog.xlsx`, 377 строк, 9 типов объектов) —
это справочник видов работ **без дат и без техники**. Обе ветки команды разложили его по 8 макроэтапам:

| | Никита: `work_map.csv` | Денис: `work_types.csv` |
|---|---|---|
| Статусы строки | substage 188 / unobservable 122 / out_of_scope 62 / header 5 | этап 1–8: 206 / исключено 168 / раздел 3 |
| Привязка | к **подэтапу** чек-листа (32 подэтапа, признаки active/done) | к макроэтапу |
| Правило | явный список кодов в checklist.json + наследование от предка | самый длинный префикс кода + ключевые слова |
| Невидимые работы | остаются в своём этапе (`unobservable`) — их даты входят в план | исключены целиком |
| Охват | здания; строки «только Дороги» — out_of_scope | по коду, без учёта типа объекта |

**Решение: канон — раскладка Никиты (`work_map.csv`)**, по трём причинам:
1. она привязывает работу к подэтапу, а у подэтапа есть признаки для модели Б — строка перечня связана
   с тем, что видно на снимке (UI показывает «12.3.1. Устройство котлована» рядом с этапом);
2. невидимая работа (геодезия, отселение) не выпадает из плана: на камере её не видно, но в графике она
   занимает дни этапа, и без неё плановые сроки этапа «худеют»;
3. в спорных строках раскладка Никиты технологически точнее (разбор ниже) — в 47 расхождениях по существу
   правота за Денисом не нашлась ни разу.

От Дениса берём одно: **запасной этап для строк «только для дорог»** (`WorkItem.fallback_stage_id`).
В перечне 62 строки отмечены лишь для «Дорог» (например, «10.11.1. Устройство ограждения строительной
площадки»), но в графике здания они встречаются; импорт относит их к этапу по коду Дениса и предупреждает.

Баг Excel «коды-даты» учтён в обе стороны: в xlsx 19 кодов второго уровня («10.1.», «12.3.») хранятся
датами (10 января, 12 марта; формат ячейки `d.m.`). В `work_map.csv` они уже исправлены, а функция
`catalog.normalize_code` чинит то же самое в чужих графиках: ячейка-дата, сериал Excel (45667),
текст «10.01.2025», «10.01», «10.янв» → «10.1.»; число 12.3 → «12.3.» с предупреждением
(«12.30» Excel уже необратимо превратил в 12.3).

## 2. Правила «этап → техника»

### 2.1. Канон — `reference/equipment_rules.json`

Основа — `equipment_expected / optional / forbidden` из checklist.json. Их одних для отклонений мало:
«ожидаемая» там означает «типичная» (на этапе 1 — пять типов сразу), и требование «все ожидаемые должны
быть на площадке» давало бы ложные тревоги. Поэтому канон разделяет роли:

| Поле | Смысл | Где используется |
|---|---|---|
| `expected` | типичная техника этапа; присутствие — довод, что этап идёт | EQUIPMENT_MISSING «нет ничего из техники этапа», EQUIPMENT_PARKED_ONLY |
| `optional` | допустимая, не аномалия | EQUIPMENT_FORBIDDEN (допустимое на любом идущем этапе не запрещено) |
| `forbidden` | не по этапу, если **задействована** (ACTIVE) | EQUIPMENT_FORBIDDEN |
| `forbidden_info` | запрещённое, но часто законная параллельная работа → info | EQUIPMENT_FORBIDDEN |
| `min_count` + `substitutes` | обязательный минимум и допустимые замены | EQUIPMENT_MISSING по типу |
| `missing_window_h` | окно (рабочие часы), за которое отсутствие — отклонение | EQUIPMENT_MISSING |
| `default_fleet` | типичный парк этапа | демо-план, плановые моточасы по умолчанию |
| `pairs` | ведущая ↔ обслуживающая техника | PAIR_BROKEN |

`norms.validate()`; тест требует пустой список.

### 2.5. Этап с учётом техники (`core/stage/fusion.py` → `core/stage/sequence.py`)

Нормы работают в обе стороны: не только «на этапе ожидается такая техника» (отклонения §5), но и «такая
техника работает — значит, идёт такой этап». Модель Б видит признаки этапа, модель А — технику; хронология
этапов (HMM по фронту 1..8) получает оба довода слагаемыми эмиссии дня.

- **Правдоподобие типа при фронте** (наивный Байес по канону §2.1): ожидаемая техника этапа — 0.6,
  допустимая — 0.25, не упомянутая — 0.08, `forbidden_info` — 0.1, запрещённая — 0.03; техника предыдущего
  этапа при новом фронте правдоподобна с множителем 0.5 (предыдущий этап часто доделывают параллельно:
  засыпка пазух при каркасе). λ(этап, тип) = ln P(тип|этап) − ln среднего по этапам: тип, ожидаемый почти
  везде (автокран, грузовик), этапа не выдаёт, тип одного этапа (копёр, каток, асфальтоукладчик) — выдаёт.
- **Сила довода за сутки**: работа по журналу моточасов 1 − e^(−ч/1 ч); тип виден, но работу не оценить
  (снимки раз в сутки) — 0.5; виден и стоит — 0.2; рамки с уверенностью < 0.5 не считаются; на камерах с
  рабочими зонами — только рамки внутри зон (техника соседней стройки этап не выдаёт).
- **Слагаемое дня** = W · clip(Σ a·λ, ±3), W — порог «Вес техники в определении этапа» (по умолчанию 1, 0 —
  только чек-лист). Отсутствие техники доводом не считается: камера видит не всю площадку, а детектор
  знает не все 21 тип (асфальтоукладчика и гусеничного крана у YOLO нет).
- **Что техника различает, а что нет.** Каток и самосвалы → благоустройство; копёр/буровая → сваи;
  башенный кран с насосом и миксерами → монолит (4 или 5 — решает чек-лист: «выше земли»). Экскаватор с
  самосвалами ожидаем на этапах 1, 3 и 8 — выбор внутри группы остаётся чек-листу (котлован виден?).
- **Защиты.** Одна техника этап не назначает (нужен хотя бы один решённый ответ модели Б); сутки с одной
  техникой (ночь, дождь) учитываются только внутри отрезка наблюдений модели Б; выбросы ищутся по
  хронологии одного чек-листа — иначе техника, удержав путь, объявила бы выбросами все кадры модели Б.
- **Объяснение** (`StageTimeline.basis` → «Почему так» на сводке и «Проверить снимок»): за последние дни на
  этапе — видимые признаки чек-листа, работающая техника с моточасами и вывод: «определён с учётом
  техники», «техника подтверждает», «техника спорит» (этап хуже лучшего по технике на ≥ 1 в сутки) или «по
  технике этап не различить». Этап, выданный техникой, получает снимки-доказательства — кадры её работы.

Замер на демо-объектах (снимок базы развёртывания, те же ответы моделей, пересчёт хронологии) — в
журнале AGENTS.md; кратко: «Асфальтирование парковки» 1 → 8, Эдинбург — совпадение хронологии с разметкой
в пределах одного этапа 81 → 96 %, «Сборный каркас», карьер и котлован двух камер не изменились.

## 3. Импорт календарного графика (`core/plan/importer.py`)

Реальный график — сотни строк с кодами перечня, детализацией без кода, сводными строками разделов,
пустыми датами и техникой свободным текстом. Импорт:

1. **Файл.** XLSX — openpyxl (берётся лист с лучшей строкой заголовков); CSV — UTF-8 (с BOM или без),
   иначе Windows-1251; разделитель `;`, `,`, табуляция определяются автоматически. `.xls` — понятный отказ.
   pandas не нужен.
2. **Заголовки** ищутся в первых 30 строках по названиям: код (`№ п/п`, «код», «шифр», code, id),
   наименование («вид работ», «наименование», name, task), начало/окончание («дата начала», «старт», «с»,
   start / «окончание», «финиш», «по», finish), длительность, техника, количество, этап. Колонки «факт» пропускаются.
3. **Коды** чинятся (`normalize_code`, §1.1); код может стоять в начале названия («12.3.1. Устройство котлована»).
4. **Сводные строки** — у которых в файле есть датированные потомки (код-продолжение или детализация) —
   не учитываются: иначе раздел «12.3.7. Земляные работы» растянул бы котлован на даты обратной засыпки (этап 4).
5. **Отнесение к этапу** — от надёжного к приблизительному, и всё приблизительное — с предупреждением:
   колонка «этап» (1–8, «4.1», название) → точный код перечня (или «родитель/название» у детализации) →
   название макроэтапа («Кровля», «1. Подготовка территории») → предок кода («12.3.7.9.» → «12.3.7.») или
   однозначное название работы → детализация наследует родителя → ключевые слова («котлован», «кровл»…) →
   номер 1–8 в колонке кода. Раздел без детализации («10. Подготовка территории») относится к этапу, только
   если все его потомки в одном этапе; иначе — предупреждение «распишите по работам».
6. **Свёртка** в 8 макроэтапов: начало = min, окончание = max, `work_codes` — ключи работ перечня,
   техника — максимум по строкам этапа (строки обычно последовательны, сумма посчитала бы машину дважды).
   Внутренние работы без этапа (отделка, внутренние сети) отбрасываются одной сводной строкой-пояснением.

Устойчивость: пустая дата (NaT, "", «-») — это `None`, а не строка `'NaT'` в базе (баг api-solution,
после которого объект переставал открываться); нераспознанная дата, начало позже окончания (даты
переставляются), неизвестный код, нераспознанная техника («кран» без уточнения, «КБ-405» — не 405 кранов),
этап без дат — каждое даёт предупреждение с номером строки. Плохой файл не бросает исключение:
пустой список и объяснение.

Пример графика в формате перечня — `reference/sample_plan.xlsx` (жилой дом 17 этажей, 35 строк,
коды второго уровня сохранены «испорченными» датами, как в xlsx организаторов; перегенерация
`python -m core.plan.sample`). Импорт даёт 8 этапов и одно предупреждение (2 строки внутренних работ).

**Демо-план** (`demo_plan(start, end, stage_ids)`) — типовой монолитный дом ~17 этажей, 510 дней,
этапы перекрываются (котлован вслед за ограждением, фасад с 2/3 каркаса, благоустройство на хвосте фасада).
Первый выбранный этап начинается с первого кадра; длительности нормальные, а если кадры охватывают больше
85 % типового срока — растягиваются так, чтобы план **кончался позже последнего кадра**. «Автоплан по датам
фото» ветки api-solution (план = [первое фото; последнее фото], на последнем кадре ожидается 100 %,
вердикт всегда «отставание») не используется.

## 4. План против факта (`core/analytics/timeline.py`)

- **Ожидаемая готовность на дату d** = Σ вес этапа × доля прошедших дней этапа / Σ весов, линейно внутри
  этапа, по концу дня d. Веса — из checklist.json (5/8/7/12/35/5/18/10).
- **Фактическая** = Σ вес × готовность этапа по модели Б (DONE = 1, ACTIVE = progress, ручная отметка
  пользователя приоритетна — её модель не перезаписывает).
- **Частичный план**: обе величины считаются **только по запланированным этапам** (баг api-solution: план
  был по этапу 5, факт — по всем 8, получалось «опережение −148 дн.» при не начатом этапе 5).
- **Отставание в днях** — сдвиг, при котором плановая кривая равна факту: D такое, что ожидаемая(D) =
  фактической; lag = сегодня − D (дробное, линейная интерполяция; на плато — ближайшая к сегодня дата).
  Если все запланированные этапы завершены — lag = фактическое окончание − плановое.
- **Вердикт**: |lag| ≤ 3 дн. — соответствие; > 3 — отставание; < −3 — опережение. Нет плана — NO_PLAN;
  нет ни одного наблюдения модели Б и ручных отметок — NO_DATA (а не ложное «отставание»).
- **Короткая съёмка** (история < 7 дн.): готовность этапа, начатого до первого кадра, за 1–2 дня снимков
  не измерить (по подэтапам выходит то 0 %, то 70 %), поэтому база — плановая готовность этого этапа на
  дату первого кадра, не больше 95 %. Вердикт тогда определяется тем, **какой этап идёт**: тот, что по
  плану, — соответствие; всё ещё предыдущий — отставание («Расчистка участка» при котловане по плану).
  Без этого «Сборный каркас» получал «отставание 10,0 дн.» — ровно дни от начала этапа до первого кадра.
- **Устаревший факт**: если этап по снимкам не обновлялся дольше 21 дня (объективы закрыты, модель Б не
  отвечает), сравнение с планом и прогноз — на дату последнего известного состояния, с пометкой в
  объяснении; иначе каждый день без наблюдений прибавлял бы день «отставания». Готовому объекту это не нужно.
- **Прогноз** (PLAN.md §3.8, «темп в активных днях»): темп — сколько дней плана стройка проходит за
  активный день в свежем окне (28 дн.), доля простоя (календарных дней на активный) — по всей истории.
  Прогноз = сегодня + (плановое окончание − D) / (темп / доля простоя). Так две недели дождя не превращают
  нормальный темп в катастрофу. Активные дни — дни с моточасами модели А (ночные смены входят); если журнал
  моточасов короче окна или пуст — календарный темп. Темп ограничен [0.2; 5]; истории < 7 дней или
  прогресса за окно нет — прогноза нет, с объяснением. Считаем по плановой кривой, а не линейно по
  процентам: ранние этапы лёгкие по весу и быстрые, их темп нельзя переносить на каркас.
- `series` для графика: дни, ожидаемая (весь план), фактическая (до сегодня), дата плана и прогноза;
  `stages` — таблица этапов план/факт со сдвигами начала и окончания.

**Объяснение вердикта** (`report.build` → `SiteReport.explanation`, 2–5 фраз): вердикт с цифрами
(«Отставание от графика ≈ 10 дней: по плану на 28.09.2026 должно быть готово 42 %, по снимкам — 35 %»), какие этапы
идут по плану (с кодами работ), что видно на снимках, прогноз окончания относительно плана, главное отклонение.

## 5. Отклонения (`core/analytics/rules.py`)

Каждое отклонение: заголовок, объяснение «**Видели:** … **По плану ожидается:** … **Что проверить:** …»,
этап, камера/зона, **снимки-доказательства** (frame_ids), единицы техники, начало и последнее подтверждение
эпизода, стабильный `key` (в ключ входит начало эпизода: продолжение — та же запись, новый эпизод — новая).
В сопоставлении с этапом участвует только ACTIVE/IDLE техника; PARKED и техника в зоне стоянки — нет.
«Идущие этапы» — по плану на сегодня или по факту модели Б, кроме уже завершённых по факту.

| Тип | Условие | Уровень | Доказательства |
|---|---|---|---|
| PAIR_BROKEN | ведущая работает (или стоит в очереди), обслуживающей нет **ни на одной камере** дольше окна пары; разрыв наблюдений > 75 мин или простой ведущей > 60 мин рвут эпизод | по паре; эскалация при долгом эпизоде | 3 кадра: начало, середина, конец; зона, камеры |
| EQUIPMENT_MISSING | нет ничего из техники этапа, или обязательного типа (с заменами) дольше окна (по умолчанию 2 рабочих часа), при ≥ 3 кадрах в окне; меньше нормы — info; тип только из плана — info, окно 1 рабочий день; отсутствие, уже объяснённое парой, не дублируется; классы, которых детектор не знает (`detectable`), не проверяются | warning, critical после 4 окон | последние кадры без этой техники |
| EQUIPMENT_FORBIDDEN | единица из `forbidden` идущего этапа **работает** (≥ 2 кадра) и не допустима ни одним идущим этапом | warning (`forbidden_info` — info) | кадры работы |
| EQUIPMENT_IDLE | обязательный тип этапа на площадке (IDLE), ни одна единица не работает, моточасы не списываются ≥ 4 рабочих часов | warning, critical ≥ 16 ч | кадры стоящей техники; «полоска» в тексте |
| EQUIPMENT_PARKED_ONLY | техника этапа есть, но вся PARKED (стоит дольше порога модели А) | warning | кадры |
| OUTSIDE_ZONE | единица в зоне `restricted` (≥ 2 кадра; и стоящая) — warning; вне всех рабочих зон и зон стоянки на камере с разметкой — info | warning / info | кадры, зона |
| HOURS_SPENT_NO_PROGRESS | моточасы типа на этапе ≥ 100 % плана (если камеры начали снимать посреди этапа — плана на наблюдаемую часть этапа), этап по модели Б не завершён и фронт не менялся ≥ 3 дн. | warning, critical ≥ 120 %; info без данных модели Б | кадры из журнала моточасов + последний кадр этапа |
| STAGE_LATE_START | плановое начало + 3 дн. прошло, признаков этапа нет (warning, critical > 14 дн.); этап начат позже плана — info | | последние кадры / кадр, где этап впервые замечен |
| STAGE_OVERDUE | плановое окончание + 3 дн. прошло, этап не завершён (warning, critical > 14 дн.); завершён с опозданием (за 30 дн.) — info | | последний кадр этапа и площадки |
| STAGE_EARLY | этап начат раньше плана > 3 дн. | info | кадр, где этап впервые замечен |
| STAGE_OUT_OF_PLAN | этап идёт по факту, а в плане его нет (пройденные до начала плана — не аномалия) | info | первый и последний кадр этапа |
| NEEDS_REVIEW | кадры с долей «затрудняюсь» > 0.5 (из хронологии модели Б): ≥ 5 — warning; кадры-выбросы хронологии — info | | сами кадры |
| CAMERA_ISSUE | живая камера молчит ≥ 2 ч (critical ≥ 24 ч); за сутки ≥ 50 % кадров брак (≥ 4 кадров); загрузки папкой/видео не «молчат» | warning / critical | последний / бракованные кадры |

Эталон ТЗ воспроизводится `core.analytics.scenarios.tz_reference()` и тестом: этап «Земляные работы,
котлован», экскаватор работает 2 ч 10 мин, самосвалов нет → PAIR_BROKEN, warning:
«Возможное снижение темпа: экскаватор работает без самосвалов 2 ч 10 мин, зона «Котлован», камеры 1, 2»
+ 3 снимка; отдельного «нет самосвалов» нет — отсутствие уже объяснено парой.

**Рабочее время** (окна и простои): по умолчанию 07:00–23:00 без выходных — в Москве шумные работы ночью
в жилой застройке запрещены, а в выходные стройки работают. Настраивается (`work_start_h`, `work_end_h`,
`workdays`, в т.ч. ночная смена через полночь). Окно пары считается по времени работы самой ведущей
техники, поэтому ночная работа экскаватора без самосвалов тоже ловится.

Все пороги — `AnalyticsConfig` (`core/analytics/context.py`), читаются из настроек площадки
(`ctx.config`, плоско или в `thresholds`).

## 6. Ограничения

- Прогноз линейный по плановой кривой: поправка на медленное начало и «хвост» этапа (PLAN.md §3.8, уровень 3)
  и каскад по цепочке этапов (уровень 4) не реализованы — нет данных для калибровки.
- История фактической готовности восстанавливается из итоговых состояний этапов (линейно от фактического
  начала); если модель Б начнёт отдавать дневные ряды готовности, темп станет точнее.
- Отсутствие техники доказывается только кадрами тех камер, что есть: если рабочую зону не видит ни одна
  камера, «нет техники» — ложная тревога (камеры и зоны — см. рекомендации по установке камер).
- Правила «этап → техника» настроены для зданий (жильё, соцобъекты, офисы); дороги вне охвата.
